# 3. Заказ, оплата, производство, счета

[← План](README.md). Согласовано: заявка → проверка файлов и подтверждение цены администратором → запрос оплаты; оплата и производство независимы; производство можно начать без оплаты; изменения до производства — по согласованию, после — нет; отмена вручную; отмена ≠ возврат; порядковые номера; EUR; Stripe с произвольной суммой и отдельным остатком ([requirements](../../requirements.md#принятые-решения-после-аудита-прототипа)).

## 3.1. От STL до заказа

1. **В браузере** (гость и клиент): файлы читаются локально, ядро `calculator.js` считает объём, габариты и оценку; до отправки на сервер ничего не уходит. Метаданные шагов — можно в `sessionStorage`; геометрия — в памяти, после перезагрузки файл выбирают заново (F-48).
2. **Отправка заявки** — один multipart-запрос: файлы, параметры по каждому файлу, пожелания, контакты, способ получения, одноразовый токен отправки (UUID из формы). Сервер:
   - проверяет лимиты до чтения тела (веб-сервер, `post_max_size`; значения — §6.4) и после (размер, число файлов, структура STL в `StlAnalyzer`);
   - пересчитывает оценку по текущим настройкам и сохраняет их снимок; клиентская сумма не используется, администратор видит серверные объём и оценку;
   - в одной транзакции создаёт корзину Lunar, строки `StlPart`, заказ через `RequestCartValidator`, порядковый номер, гостевой токен, событие для Sheets и письма на info@aiqme.com;
   - повтор токена отправки возвращает тот же заказ (уникальный `order_meta.submission_token`, §2.5); другие данные с тем же токеном (`submission_digest`) отклоняются. Для гостя повтор перевыпускает гостевой токен (§6.2): новая ссылка показывается один раз, прежняя перестаёт работать (рабочей остаётся последняя показанная);
   - отправка защищена как формы W-09: honeypot (ложного успеха с номером нет) и ограничение частоты по IP (настройка `config/aiqme.php` из `.env`, по умолчанию 10 заявок в час); превышение — 429 без записи файлов, заказа, письма и события.
3. **Результат**: страница подтверждения с номером заказа; гостю — секретная ссылка на заказ с советом сохранить её; клиент видит заказ в кабинете.

**Порядковый номер** — целое из счётчика `counters`, выдаётся атомарным `UPDATE … SET value = value + 1 RETURNING value` в транзакции заявки (первый номер — настройка, по умолчанию 1; при откате не расходуется); генератор номеров Lunar пишет его в `reference`. Номер не даёт доступа к заказу.

**Подготовительная плата** (D-08, рекомендация): `оценка = Σ(mass_i × rate) + плата_за_заказ + n × плата_за_файл` (плата за файл по умолчанию 0), где `rate` — **одна общая цена за грамм** для всех материалов (как `data-price-per-gram` в `calculator.js`); материалы различаются только плотностью. Тарифы — настройки админки.

**Строки заказа Lunar.** Файл — строка `StlPart`. Плата за заказ и за файлы — одна служебная строка `OrderCharge` (Purchasable по образцу `StlPart`) вида `fee` (W-12); доставка — строка вида `delivery`, её добавляет администратор при подтверждении цены (§3.2, W-13). Сумма заказа и подтверждённая цена = сумма всех строк; «Every line needs a price» эксперимента — для всех строк, включая служебные. Согласование с переносимым кодом:
- лимит 10 строк `RequestCartValidator` и проверка «purchasable — `StlPart` владельца» — только по строкам `StlPart`;
- `fee` не создаётся при сумме 0; при подтверждении цены ей можно поставить 0 (требование `confirmPrice` «цена > 0» к `fee` не применяется);
- `delivery` создаётся как `OrderLine` (purchasable `OrderCharge`) размещённого заказа в транзакции `confirmPrice`, не через корзину; одна на заказ: ревизия цены меняет её цену (или создаёт, если нет), удаления в MVP нет.

**Масса и округление до центов** (одинаково в JS и PHP, тот же порядок операций):
- объём файла V — модуль суммы `(a−o)·((b−o)×(c−o))/6` по треугольникам в порядке файла, `o` — первая вершина (как в `calculator.js`), в единицах файла; см³ = `V × k × k × k / 1000`, `k = мм_на_единицу × масштаб / 100` (единицы и масштаб — к объёму, не к координатам);
- `mass_i = V × плотность × (0,2 + 0,8 × заполнение/100) × qty` (0,2 и 0,8 — константы ядра; в настройках только заполнение по умолчанию, %);
- оценка строки в центах = `floor(x + 0,5)` (half-up), `x = mass_i × rate × 100` в IEEE double в этом порядке (`rate` хранится десятичной строкой, переводится в double; без `bcmath` и decimal); плата за заказ и за файл — целые центы; итог = сумма строк + плата за заказ + n × плата за файл. Дробные центы не хранятся и не суммируются; на экране — EUR с двумя знаками;
- контрольные примеры (PLA, 100 %, 0,10 EUR/г, 5 EUR): 1 см³, qty 1 → 1,24 г, строка 12 центов, итог 512 центов (5,12 EUR); 1 см³, qty 3 → 3,72 г, строка 37 центов (не 3 × 12);
- строка `StlPart` в корзине и заказе Lunar — те же центы и всегда quantity = 1; количество — в `parameters.quantity` (проверка валидатора 1–100 — по нему); при подтверждении цены администратор вводит цену строки целиком.

До реальных тарифов (D-09) — примерные 0,10 EUR/г и 5 EUR с пометкой «не подтверждено» в админке; на странице — «предварительная оценка».

## 3.2. Подтверждённая цена

- Администратор проверяет файлы (скачивает STL), вводит цену по каждой строке и при доставке — строку «Pristatymas / Delivery». Заказ получает `confirmed_at` и ревизию 1.
- До `started_at` цену можно изменить с основанием и ссылкой на согласование с клиентом (текст вроде «согласовано по телефону 18.10» или ссылка на ответ клиента «согласен с изменением», §1.3, W-13; сам ответ цену не меняет). Изменение пишется в `price_revisions` и журнал.
- Новая цена не ниже оплаченного (иначе нужен возврат, D-07) и оставляет остаток (цена − оплачено) 0 или ≥ 0,50 EUR (минимум запроса §3.3); иначе изменение не сохраняется, администратор видит понятное сообщение.
- Пока есть открытый платёжный запрос, цену изменить нельзя: сначала запрос отменяется.
- После выпуска счёта (§3.5, W-17) цена заблокирована так же, как после `started_at`, с понятным сообщением.
- Срока действия цены нет (D-06): цена действует, пока заказ не изменён.

## 3.3. Платёжные запросы и Stripe

| Шаг | Правило |
|---|---|
| Создание запроса | Только администратор, после подтверждения цены, не для отменённого заказа. Сумма ≥ 0,50 EUR (минимум Stripe для EUR, иначе `amount_too_small`; константа в коде) и ≤ подтверждённая цена − оплачено − другие открытые запросы; остаток после запроса — 0 или ≥ 0,50 EUR; иначе запрос не создаётся, администратор видит понятное сообщение. Полная сумма или произвольный аванс (процент не фиксирован); остаток — новым запросом. Запрос сразу в `pending` **без обращения к Stripe** (`stripe_intent_id` пуст) |
| Сообщение клиенту | Автоматического письма нет (В-052). Клиент видит запрос и кнопку оплаты в кабинете или на гостевой странице. Администратор сообщает о запросе своим каналом (D-10): клиенту — ссылку на страницу оплаты (нужен вход); гостю — **гостевую ссылку заказа**, не ссылку оплаты (по `public_id` гость без права в сессии получит 404). Гостевая ссылка получается только перевыпуском (открытый токен не хранится, §6.2): новая показывается один раз с предупреждением, что прежняя перестаёт работать. С гостевой страницы (право в сессии) гость переходит к оплате |
| Страница оплаты | `/lt/apmokejimas/<public_id>` · `/en/checkout/<public_id>`: заказ, сумма запроса, Stripe Payment Element. Карточные данные не проходят через AIQME. Доступ — владелец, администратор или гость с правом на заказ в сессии (§6.2); остальным — 404. Администратор видит страницу без Payment Element: intent при его открытии не создаётся |
| Создание PaymentIntent | При **первом открытии страницы оплаты** клиентом, не при создании запроса. Ключи Stripe не заданы (проверка до транзакции 1) — «оплата временно недоступна», состояние не меняется. Транзакция 1 — блокировка и проверка запроса, `pending → creating`, сохранение ключа; вызов Stripe вне транзакции БД (§2.6); транзакция 2 блокирует строку запроса и сохраняет `intent_id`: `creating → pending` и выдача `client_secret` — только если запрос всё ещё `creating` и заказ не отменён; иначе `client_secret` не выдаётся («запрос закрыт»): при отменённом заказе — `creating → cancelling` и отмена intent по автомату, при `void` — состояние не меняется, intent отменяется в Stripe после commit. `capture_method=automatic` (**manual capture не используется**); только карта: `payment_method_types = ['card']` (D-33; `automatic_payment_methods` эксперимента не переносится; кошельки — D-42). Сумма и валюта — только из `payment_requests`; metadata: `request_id` (= `public_id`), `order_id`; idempotency key `aiqme-request-<public_id>`. Повторное открытие продолжает тот же intent: `retrieve` вне транзакции; при `succeeded` или `processing` — «платёж обрабатывается» без формы, ничего не записывается (записывают webhook или кнопка администратора) |
| Подтверждение | Только проверенный webhook (`Stripe-Signature` по сырому телу, допуск по времени) или авторизованное чтение intent через API (кнопка администратора «проверить статус в Stripe» для запросов в `creating`, `cancelling` и `pending` с intent; ответ Stripe при отмене). Возврат браузера, `paid=1` и действие администратора оплату не подтверждают: при `redirect_status=succeeded` или `processing` — «платёж обрабатывается» без формы, ничего не записывается |
| Проверки события | После проверки подписи и `livemode`. **Версия API**: endpoint — `2025-02-24.acacia` (`Stripe\Util\ApiVersion::CURRENT` SDK 16.6.0, §5.5); событие с `api_version` старше `2022-11-15` (нет `latest_charge`) — `result = needs_review` без `capture`, на сверке (не исход 4). **Деньги получены** — `payment_intent.succeeded`, `status = succeeded`, `amount_received > 0`, `latest_charge` есть. Запрос — по `metadata.request_id`. **Совпадение** — запрос найден; его `stripe_intent_id` равен id intent или пуст у запроса в `creating` (id берётся из события; пустой у `pending` — несовпадение, исход 2); `metadata.order_id` = заказ запроса; `amount` и `amount_received` = сумма запроса; валюта EUR |
| Ответ webhook | Неподписанное, с чужим секретом или live-событие в нерабочей среде — 400 без записи. Подписанное событие всегда записывается в `payment_events` и получает 200 (422 эксперимента не переносится: Stripe повторял бы событие до трёх суток). Исход решает факт денег, а не совпадение полей. В исходах 1 и 2 сначала проверяется заряд `latest_charge` (строка «Запись»): уже записан по этому запросу — повтор без эффекта; по другому запросу — без `capture`, `result = needs_review`, `needs_review = true` у запроса события. (1) Деньги получены и совпадение — `result = applied`, `capture` на `amount_received`, запрос → `paid`. (2) Деньги получены, запрос найден, валюта EUR, но intent, `order_id` или сумма не совпадают — тоже `capture` на заказ запроса, запрос → `paid` (если ещё не), `needs_review = true` с `review_reason`, `result = needs_review`. (3) Деньги получены, но запрос не найден или валюта не EUR — без `capture`, `result = needs_review`, у найденного запроса `needs_review = true`. (4) `succeeded` без денег (`status` ≠ `succeeded`, `amount_received = 0` или нет `latest_charge`) — `result = rejected`, без изменений. (5) `payment_intent.payment_failed` и прочие типы, кроме `charge.refunded` («Возвраты»), — `result = ignored`, без изменений; `payment_failed` по найденному неоплаченному запросу пишет событие §5.1 «оплата не прошла» (после `paid` — нет). Переплата — оплат по заказу больше подтверждённой цены. Тест эксперимента `test_bad_signature_and_wrong_amount_currency_or_intent_are_rejected` (запрос 4000 в `pending` с intent) переносится пятью отдельными тестами, каждый со своим свежим запросом и своим `latest_charge`: `amount=1` — исход 2; `currency=usd` — исход 3; `id=pi_other` — исход 2; `amount_received=0` и `status=processing` — исход 4 |
| Запись | Транзакция Lunar `capture` (`reference` = id заряда `latest_charge`, `meta.request_id`), запрос → `paid`. Заряд хранится на транзакции, не в `payment_requests`. Уникальность события — PK `payment_events.event_id` (§2.5), заряда — частичный уникальный индекс `lunar_transactions (reference) WHERE type = 'capture'` (миграция AIQME, `vendor/` не меняется). Повтор события — без эффекта (кроме повтора `charge.refunded` с прежним `needs_review`, «Возвраты»). Новое событие с зарядом, записанным по другому запросу, — 200, без `capture`, `result = needs_review`, `needs_review = true` у запроса события (исключение из `test_same_charge_cannot_pay_another_request` эксперимента не переносится). Второе списание по тому же запросу (другой заряд) — свой `capture` («Аномалии»). Поздний `payment_failed` после успеха списание не отменяет. После любой записи `capture`: оплачено (за вычетом возвратов) больше подтверждённой цены — `needs_review = true`, `review_reason = overpaid` |
| Аномалии | Оплата отменённого заказа, переплата, второе списание по тому же запросу (другой intent), `succeeded` для запроса в `cancelling`/`void` при отменённом заказе — по исходам «Ответа webhook»: `capture`, если деньги получены и известен запрос с валютой EUR, плюс `payment_requests.needs_review = true` с `review_reason` (состояние — по автомату ниже); запрос не найден или валюта не EUR — без `capture`, `payment_events.result = needs_review`. Overview показывает обе выборки; производство не запускается; webhook отвечает 200 |
| Отмена запроса | Без intent: `pending → void` в одной транзакции, без Stripe. С intent: транзакция 1 — `pending → cancelling` (новый intent не создаётся, страница оплаты закрыта); после commit — отмена PaymentIntent в Stripe; транзакция 2 — `cancelling → void`. Ответ «intent уже оплачен» — исключение `InvalidRequestException` с кодом `payment_intent_unexpected_state` (мок W-16 бросает именно его): после него `retrieve` вне транзакции; `succeeded` с `latest_charge` — запись оплаты, `canceled` — `void`. Оплата записывается и при проверенном `payment_intent.succeeded` для запроса в `cancelling` или `void`: `capture`, запрос → `paid` (из `void` тоже); заказ отменён — ещё `needs_review = true`. Stripe недоступен — запрос остаётся `cancelling`; кнопка «проверить статус в Stripe» сначала `retrieve`: `succeeded` с `latest_charge` — запись оплаты; `canceled` — `cancelling → void` (повторная отмена дала бы `payment_intent_unexpected_state`); отменяемый статус — повтор отмены; иной — остаётся `cancelling`, ошибка видна администратору. Запрос в `creating` сначала проверяется в Stripe (поиск по `metadata.request_id`): найден — `creating → pending` и отмена как выше; не найден — `creating → void` (отставание Search API не мешает: `client_secret` не выдавался; если всё же придёт проверенное `succeeded` — `void → paid`) |
| Неизвестный исход | Таймаут, 5xx или окончательная 4xx при создании intent → запрос остаётся `creating` («проверяется»); второй intent не создаётся. Открытие страницы при `creating` (и второй вкладкой) показывает «проверяется», Stripe не вызывает. Повтор — только кнопкой администратора «проверить статус в Stripe»: поиск intent по `metadata.request_id`; найден — `creating → pending`; не найден и с `intent_first_attempt_at` (§2.5) прошло меньше 24 часов (срок ключа идемпотентности Stripe; Search API отстаёт до минуты) — повтор создания с тем же ключом; позже — `creating → void` с `needs_review = true`, администратор создаёт новый запрос |
| Возвраты | В MVP — вручную в Stripe Dashboard (D-07, рекомендация); кнопки возврата в AIQME нет. Webhook `charge.refunded` (объект — Charge, `amount_refunded` накопительный, `refunds` по умолчанию не включён) записывает транзакцию Lunar `refund` и уменьшает «оплачено». Заряд ищется только как `capture` с `reference` = id заряда (так находится и второе списание), запрос — по её `meta.request_id`; поиска по `payment_intent` нет — заряд без `capture` (например, исход 3) «оплачено» не уменьшает. Под той же блокировкой строки запроса, что и `capture`: сумма `refund` (`reference` = id заряда, `parent_transaction_id` = эта `capture`) = `amount_refunded` − уже записанные `refund` с этим `reference`; разница ≤ 0 — без эффекта; `result = applied`; заряд не найден — `result = needs_review`. Повтор `charge.refunded` с прежним `needs_review` и пустым `reviewed_at` обрабатывается заново: возврат, пришедший раньше `payment_intent.succeeded`, учитывается повторной отправкой события из Dashboard |
| Оплата и производство | Успешная оплата не запускает производство и не меняет стадию. Отмена заказа не делает возврат |

**Автомат `payment_requests.state`.** `pending` — открыт для оплаты (без intent или с `intent_id`); `creating` — только между транзакциями 1 и 2 создания intent и при неизвестном исходе. Переходы (других нет):
- `pending → creating` — первое открытие страницы оплаты без intent;
- `creating → pending` — intent создан или найден по ключу/`request_id`, `intent_id` сохранён;
- `creating → void` — при отмене запроса intent не найден по `request_id` («Отмена запроса») или не найден спустя 24 часа после `intent_first_attempt_at`;
- `pending → void` — отмена без intent; `pending → cancelling → void` — отмена с intent; `creating → cancelling` — транзакция 2 при отменённом заказе;
- `pending/creating/cancelling/void → paid` — проверенное `succeeded` или ответ «уже оплачено» (`intent_id` из события).

Открытые — `pending`, `creating`, `cancelling`; `paid` — конечное. `needs_review` — флаг, не состояние: `state` не меняет, снимается действием администратора «разобрано» с записью в журнал (W-28); так же отмечается разобранным событие `payment_events` с `result = needs_review` (`reviewed_at`).

Состояние оплаты выводится из транзакций: `unpaid` / `partial` / `paid` / `overpaid`, плюс долг = подтверждённая цена − оплачено.

## 3.4. Производство и передача

Стадии из прототипа, отдельно от оплаты (демо-цепочка `Paid → Technical review` не переносится):

`review` (заявка, проверка файлов) → `confirmed` (цена подтверждена) → `in_production` → `quality_check` → `ready` (готов к отправке или самовывозу) → `shipped` (только при доставке; нужен трек-номер и перевозчик) → `completed`. Из любой стадии до `completed` — `cancelled`.

- Переходы — только вперёд; самовывоз — из `ready` прямо в `completed`.
- Начать производство можно без оплаты (В-003); если долг не погашен, система спрашивает подтверждение.
- После `in_production` цена и состав заблокированы.
- Отмена: только администратор, с причиной; открытые запросы отменяются по §3.3 «Отмена запроса»: `pending` без intent — `void` в той же транзакции (W-13); с intent — через `cancelling` и Stripe после commit (W-16); `creating` — после commit проверка в Stripe (найден — `creating → pending → cancelling → void`, не найден — `void`; Stripe недоступен — остаётся `creating` до кнопки «проверить статус в Stripe»); идущее создание intent `client_secret` не выдаёт (§3.3 «Создание PaymentIntent», W-16). Деньги автоматически не возвращаются, в карточке остаётся «оплачено X EUR».
- Трек вводится вручную и виден клиенту. Ярлыков, упаковки и API перевозчиков нет.
- Bambu: лист задания (параметры, пожелания, ссылки на файлы через защищённую выдачу) — без автоматической передачи на принтер.
- Частичное выполнение и частичная отгрузка не делаются (В-026 — простой вариант).
- Напоминаний и автоматического закрытия нет (В-033).

## 3.5. Счета

Автоматические счета обязательны; реквизиты, налоги и нумерация — в настройках. Момент выпуска, сроки оплаты и правила возврата **не согласованы**.

| Часть | Решение |
|---|---|
| Генерация | `InvoiceService`: снимок реквизитов продавца и покупателя (физлицо или компания: имя, код, VAT-код, адрес; адрес покупателя — из заявки или профиля, если есть, иначе счёт без адреса, D-23), позиции, суммы, VAT по настройкам; PDF через dompdf из Blade-шаблона без внешних ресурсов, шрифт DejaVu Sans (литовские символы), на языке заявки (локаль из `order_meta`, §2.5; LT/EN). Базовый PDF заказа Lunar счётом не считается |
| Номер | Серия + следующий номер из настроек, атомарный `UPDATE … RETURNING` счётчика в транзакции выпуска. Номер, строка счёта и PDF — в одной транзакции задания: ошибка PDF откатывает её (номер не расходуется и не дублируется), повтор задания выпускает счёт заново; повтор события или рендера номер не меняет |
| Неизменность | Выпущенный счёт не перезаписывается; после выпуска цена заказа заблокирована (§3.2). Исправление — новый документ, связанный с исходным (кредитовый счёт — при определении правил возврата) |
| Без реквизитов | Реквизиты продавца, VAT-статус или нумерация не заданы — выпуск **блокируется**, в админке предупреждение; после сохранения реквизитов ожидающие счета выпускает задание (W-17). Вымышленные значения не подставляются |
| Момент выпуска (D-04) | По умолчанию (рекомендация; настраиваемо): итоговый счёт-фактура на подтверждённую сумму, когда оплачено ≥ подтверждённой цены. Идемпотентная проверка `InvoiceService::issueIfDue(order)` — задание очереди `afterCommit` после записи `capture`, `refund` и изменения цены, а также задание «ожидающие счета» (после сохранения реквизитов и раз в сутки). Сбой PDF не даёт 500 на webhook: задание повторяется, неудача видна в Overview, номер не меняется. Условия выпуска: счёта ещё нет, цена подтверждена, оплачено ≥ подтверждённой цены, заказ не отменён (отменённый оплаченный — без счёта, на сверке); так счёт выпускается и при снижении цены до оплаченного, и при переплате (W-17). Для каждого аванса карточка заказа (кабинет и гостевая страница) показывает подтверждение платежа «дата, сумма» из транзакций, без PDF и номера (W-15). До рабочего выпуска — подтверждение бухгалтера |
| VAT | Ставка и статус плательщика — настройки (D-05). Подтверждённая цена и платёжные запросы — **с VAT** (D-22): счёт выделяет VAT из каждой строки (VAT строки в центах = `floor(брутто × ставка / (100 + ставка) + 0,5)`, нетто = брутто − VAT); итог счёта всегда = подтверждённая цена (излишек переплаты — на сверке); продавец не плательщик — VAT 0 с пометкой из настроек. Демо-21 % не используется. Обратного начисления для компаний ЕС нет — одна ставка для всех (D-34). Stripe Tax и Stripe Invoicing не применяются |
| Доступ | Клиент скачивает свои счета в кабинете, гость — с гостевой страницы заказа по праву в сессии (§6.2; токена в адресе файла нет), администратор — все; выдача с проверкой прав |
| Sheets | Номер счёта попадает в строку заказа |

TEJA — после релиза; Google Таблицы бухгалтерские функции не заменяют.
