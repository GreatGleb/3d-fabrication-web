# 3. Заказ, оплата, производство, счета

[← План](README.md). Согласовано: заявка → проверка файлов и подтверждение цены администратором → запрос оплаты; оплата и производство независимы; производство можно начать без оплаты; изменения до производства — по согласованию, после — нет; отмена вручную; отмена ≠ возврат; порядковые номера; EUR; Stripe с произвольной суммой и отдельным остатком ([requirements](../../requirements.md#принятые-решения-после-аудита-прототипа)).

## 3.1. От STL до заказа

1. **В браузере** (гость и клиент): файлы читаются локально, ядро `calculator.js` считает объём, габариты и оценку. На сервер до отправки ничего не уходит. Метаданные шагов можно держать в `sessionStorage`; геометрия — в памяти, после перезагрузки файл выбирают заново (как в прототипе, F-48).
2. **Отправка заявки** — один multipart-запрос: файлы, параметры по каждому файлу, пожелания, контакты, способ получения, одноразовый токен отправки (UUID из формы). Сервер:
   - проверяет лимиты до чтения тела (веб-сервер, `post_max_size`) и после (размер, число файлов, структура STL в `StlAnalyzer`);
   - пересчитывает оценку на сервере по текущим настройкам и сохраняет их снимок. Клиентская сумма не используется: администратор видит серверные объём и оценку;
   - в одной транзакции создаёт корзину Lunar, строки `StlPart`, заказ через `RequestCartValidator`, порядковый номер, гостевой токен, событие для Sheets и письма на info@aiqme.com;
   - повтор того же токена отправки возвращает тот же заказ; другой набор данных с тем же токеном отклоняется.
3. **Результат**: страница подтверждения с номером заказа. Гостю показывается секретная ссылка на заказ с советом сохранить её. Зарегистрированный клиент видит заказ в кабинете.

**Порядковый номер** — целое число из отдельного счётчика с блокировкой строки (первый номер задаётся в настройках, по умолчанию 1). Через генератор номеров Lunar он записывается в `reference`. Номер не даёт доступа к заказу.

**Подготовительная плата для нескольких STL** (D-08, рекомендация): одна плата на заказ и отдельная настраиваемая плата за каждый файл (по умолчанию 0). Прежняя формула `mass × rate + fee` применялась к одному файлу; теперь `оценка = Σ(mass_i × rate_i) + плата_за_заказ + n × плата_за_файл`. Тарифы — настройки админки. До получения реальных тарифов (D-09) используются существующие примерные значения 0,10 EUR/г и 5 EUR с пометкой «не подтверждено» в админке. На странице результат подписан как предварительная оценка.

## 3.2. Подтверждённая цена

- Администратор проверяет файлы (скачивает STL), вводит цену по каждой строке и при доставке — строку «Pristatymas / Delivery». Заказ получает `confirmed_at` и ревизию 1.
- До `started_at` цену можно изменить. Нужны основание и ссылка на согласование с клиентом (текст: «согласовано по телефону 18.10» и т. п.). Ответ клиента в карточке заказа тоже фиксируется как согласование. Изменение пишется в `price_revisions` и журнал.
- Новая цена не может быть ниже уже оплаченного: такое уменьшение требует возврата (D-07) и в MVP блокируется с понятным сообщением.
- Пока есть открытый платёжный запрос, цену изменить нельзя: сначала запрос отменяется.
- Срока действия цены нет (D-06): цена действует, пока заказ не изменён.

## 3.3. Платёжные запросы и Stripe

| Шаг | Правило |
|---|---|
| Создание запроса | Только администратор, только после подтверждения цены, не для отменённого заказа. Сумма > 0 и ≤ (подтверждённая цена − оплачено − другие открытые запросы). Полная сумма или произвольный аванс; остаток — новым запросом. Процент не фиксирован |
| Сообщение клиенту | Автоматического письма нет (В-052: только запрошенные уведомления). Клиент видит запрос в кабинете или на гостевой странице. Администратор копирует ссылку и отправляет её своим каналом (D-10) |
| Страница оплаты | `/lt/apmokejimas/<public_id>` · `/en/checkout/<public_id>`: заказ, сумма запроса, Stripe Payment Element. Карточные данные не проходят через AIQME. Доступ — владелец, администратор или гостевой токен |
| Создание PaymentIntent | Автоматическое списание (`capture_method=automatic`); **manual capture не используется**. Сумма и валюта только из `payment_requests`. metadata: `request_id`, `order_id`. Idempotency key = `aiqme-request-<public_id>`. Повторное открытие страницы продолжает тот же intent. Сетевой вызов — вне транзакции БД (§2.6) |
| Подтверждение | Только проверенный webhook (`Stripe-Signature` по сырому телу, допуск по времени) или авторизованное чтение intent через API. Возврат браузера со страницы оплаты, параметр `paid=1` и действие администратора оплату не подтверждают |
| Проверки события | `livemode` соответствует среде; intent совпадает с запросом; `order_id` из metadata совпадает; `amount_received` = сумма запроса; валюта EUR; `latest_charge` есть |
| Запись | Транзакция Lunar `capture`, запрос → `paid`; уникальность `event_id` и `provider_reference`. Повтор события — без эффекта. Поздний `payment_failed` после успеха не отменяет списание |
| Аномалии | Оплата отменённого заказа, переплата, второе списание по тому же запросу, неизвестный intent из metadata — записываются с пометкой `needs_review`, видны в Overview; производство не запускается; webhook отвечает 200 |
| Отмена запроса | Администратор отменяет открытый запрос: в БД `void`, затем отмена PaymentIntent в Stripe. Если Stripe сообщает, что оплата уже прошла, — запрос остаётся `paid` |
| Неизвестный исход | Таймаут или 5xx при создании → состояние «проверяется»; повтор с тем же ключом или чтение intent по `request_id`; второй intent на тот же запрос не создаётся. В админке есть кнопка «проверить статус в Stripe» |
| Возвраты | В MVP — вручную в Stripe Dashboard (D-07, рекомендация). Webhook `charge.refunded` записывает транзакцию Lunar `refund` и уменьшает «оплачено». Кнопки возврата в AIQME нет |
| Оплата и производство | Успешная оплата не запускает производство и не меняет стадию. Отмена заказа не делает возврат |

Состояние оплаты выводится из транзакций: `unpaid` / `partial` / `paid` / `overpaid`, плюс долг = подтверждённая цена − оплачено.

## 3.4. Производство и передача

Стадии из прототипа без смешения с оплатой (демо-цепочка `Paid → Technical review` буквально не переносится):

`review` (заявка, проверка файлов) → `confirmed` (цена подтверждена) → `in_production` → `quality_check` → `ready` (готов к отправке или самовывозу) → `shipped` (только при доставке; нужен трек-номер и перевозчик) → `completed`. Из любой стадии до `completed` — `cancelled`.

- Переходы — только вперёд по цепочке. Возврат на шаг назад не нужен. Самовывоз идёт из `ready` прямо в `completed`, как в прототипе.
- Начать производство можно без оплаты (В-003); если долг не погашен, система спрашивает подтверждение.
- После `in_production` цена и состав заблокированы.
- Отмена: только администратор, с причиной; открытые платёжные запросы отменяются; деньги не возвращаются автоматически, в карточке остаётся «оплачено X EUR».
- Трек вводится вручную и виден клиенту. Ярлыков, упаковки и API перевозчиков нет.
- Bambu: лист задания (параметры, пожелания, ссылки на файлы через защищённую выдачу) — без автоматической передачи на принтер.
- Частичное выполнение и частичная отгрузка не делаются (В-026 — простой вариант).
- Напоминаний и автоматического закрытия нет (В-033).

## 3.5. Счета

Автоматические счета обязательны; реквизиты, налоги и нумерация задаются в настройках. Момент выпуска, сроки оплаты и правила возврата **не согласованы**.

| Часть | Решение |
|---|---|
| Генерация | `InvoiceService`: снимок реквизитов продавца и покупателя (физлицо или компания: имя, код, VAT-код, адрес), позиции, суммы, VAT по настройкам; PDF через dompdf из Blade-шаблона без внешних ресурсов, LT/EN. Базовый PDF заказа Lunar счётом не считается |
| Номер | Серия + следующий номер из настроек, выдаётся в транзакции с блокировкой. Повтор события или повтор рендера номер не меняет; ошибка PDF не создаёт второй номер |
| Неизменность | Выпущенный счёт не перезаписывается. Исправление — новый документ, связанный с исходным (кредитовый счёт — при определении правил возврата) |
| Без реквизитов | Если реквизиты продавца, VAT-статус или нумерация не заданы, выпуск **блокируется**: в админке предупреждение, событие ждёт. Вымышленные значения не подставляются |
| Момент выпуска (D-04) | Рекомендуемый вариант по умолчанию, настраиваемый: итоговый счёт-фактура на подтверждённую сумму при достижении `paid`. Для каждого поступившего аванса в кабинете показывается подтверждение платежа без номера счёта. Требует подтверждения бухгалтером до рабочего выпуска |
| VAT | Ставка и статус плательщика — настройки (D-05). Демо-21 % не используется. Stripe Tax и Stripe Invoicing не применяются |
| Доступ | Клиент скачивает свои счета в кабинете, гость — по ссылке заказа, администратор — все; выдача с проверкой прав |
| Sheets | Номер счёта попадает в строку заказа |

TEJA — после релиза; Google Таблицы бухгалтерские функции не заменяют.
