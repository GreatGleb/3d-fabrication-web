# Оставшиеся решения

[← План](README.md). Список для разработчика (Глеба). Заказчику сейчас вопросов не задаём; возражения после передачи исправляются обновлениями. Для каждого пункта указан **вариант по умолчанию**: с ним задачи выполняются без ожидания; отклонение — только по новому указанию пользователя. Вариант по умолчанию — рекомендация, а не согласие заказчика или бухгалтера. Пункты с пометкой «данные» нельзя закрыть выбором: нужны реальные сведения, вымышленные рабочие значения запрещены. История обсуждения и раунды проверки — в [changes.md](changes.md).

Статус: **П** — подтверждено пользователем 19.10 (вариант по умолчанию); **Р** — вариант по умолчанию принят пользователем 19.10 для разработки, ответ заказчика (для VAT и счёта — бухгалтера) нужен к рабочему запуску W-23, вопрос — в отложенных сведениях [опросника](../questions-for-owner.md); пусто — рекомендация. Файлы ночного прогона — каталог `run/` (ссылки в D-28 и D-39).

### D-01

**Хостинг.** VPS в ЕС, Ubuntu LTS, отдельный Docker Compose на каждый проект, общий обратный прокси с TLS, лимиты ресурсов на контейнеры ([§8.1](08-operations.md#81-размещение-d-01-рекомендация)). Размер — сумма требований проектов; строка AIQME — в W-29, нагрузку другого проекта не придумываем. Почему: сервер не арендован, на нём будут другие сайты, включая более крупный проект.

### D-02

**БД.** PostgreSQL 17, отдельная БД и роль. Почему: проверен экспериментом (доказательство работоспособности эксперимента, а не утверждение). Альтернатива — общий кластер крупного проекта с отдельной БД и ролью.

### D-03

**Фоновое выполнение.** Драйвер очереди `database`, один процесс `queue:work`, `schedule:run` раз в минуту. Redis — только если он уже нужен на сервере другим проектам и выделен отдельной БД/префиксом.

### D-04

**Счёт.** По умолчанию (настраиваемо): итоговый счёт-фактура на подтверждённую сумму при полной оплате; для авансов — подтверждение платежа в кабинете без номера счёта. Почему: момент выпуска и виды документов не определены; до рабочего выпуска нужен ответ бухгалтера — сейчас не запрашиваем. Альтернативы: счёт на каждый платёж; проформа при запросе оплаты.

### D-05

**Данные: реквизиты продавца, статус плательщика VAT и ставка, серия и начальный номер счетов.** Без них выпуск счёта блокируется, в админке предупреждение. Демо-НДС 21 % не используется; Stripe Tax и Stripe Invoicing не выбраны.

### D-06

**Сроки.** Автоматических сроков нет: платёжный запрос открыт, пока администратор его не отменит; цена действует, пока заказ не изменён. Напоминаний и автозакрытия нет (В-033).

### D-07

**Возвраты.** Возврат выполняется вручную в Stripe Dashboard; AIQME записывает его по webhook `charge.refunded` как транзакцию возврата и показывает. Кнопки возврата в AIQME нет; отмена заказа деньги не возвращает; уменьшение цены ниже оплаченного блокируется. Почему: правила возвратов не определены.

### D-08

**Подготовительная плата для нескольких STL.** `оценка = Σ масс × цена за грамм + плата за заказ + число файлов × плата за файл`; цена за грамм одна для всех материалов, как в `calculator.js` (§3.1). Плата за файл по умолчанию 0, поэтому прежние 5 EUR берутся один раз на заказ. Оба значения — настройки админки.

### D-09

**Данные: реальные тарифы, материалы и плотности.** До их получения — существующие примерные значения ядра в EUR (PLA 1,24, ABS 1,04, PETG 1,27 г/см³; 0,10 за грамм; плата 5; заполнение по умолчанию 20 %, как в прототипе и прежнем калькуляторе) с пометкой «не подтверждено» в админке. На сайте результат подписан как предварительная оценка; окончательную цену подтверждает администратор.

### D-10

**Гостевой доступ.** После отправки гость получает секретную ссылку на заказ; открытый токен не хранится, поэтому администратор передаёт ссылку только перевыпуском (новая показывается один раз, прежняя перестаёт работать; §3.3, §6.2). Автоматических писем клиенту (подтверждение, запрос оплаты) нет; о запросе оплаты администратор сообщает своим каналом; привязки гостевого заказа к аккаунту нет. Почему: так ограничен объём уведомлений (В-052). Письмо клиенту о запросе оплаты, если его захочет заказчик, — небольшое добавление в W-16.

### D-11

**Исходный контент.** Тексты услуг, главной, «О нас», FAQ и 3 статей импортируются из прототипа. Три иллюстративных проекта и политики (помечены в прототипе как демонстрационные) импортируются **черновиками**, а разделы показывают согласованную заглушку до публикации реального материала (расширение правила заглушек, отменяется публикацией); так же — демо-расписание обучения (D-21). Cookie — только необходимые, поэтому вместо выбора аналитики — информационная плашка.

### D-12

**Продажа товаров каталога** выключена: опубликованная карточка показывает товар и «Запросить предложение»; корзина товаров — пустое состояние со ссылкой на калькулятор. Почему: правила продажи и склада не утверждены, демо-ассортимент не продаётся. Включение продаж — отдельная задача (связь карточки с вариантом Lunar, цена, налоги, доставка).

### D-13

**Хранение.** Модели зарегистрированных клиентов — до удаления (решено). Копия ежедневно, 14 дневных + 8 недельных на сервере и копия вне сервера в хранилище владельца; документы и заказы автоматически не удаляются. Место внешней копии — данные владельца.

### D-14

**Исходники.** Весь корень рабочего пространства — в **публичном** репозитории `GreatGleb/3d-fabrication-web` (решение пользователя 18.10; тот же, где прежний лендинг; Pages раздаёт сборки из папок). Приватное (переписка и материалы заказчика, аудит и исходники прототипа, исторический цикл плана, `instance/`, `.env`, снимки-архивы) исключено корневым `.gitignore`; секреты и реальные данные в код не попадают никогда. Передача заказчику — копией или зеркалом на его аккаунт (аккаунты будут принадлежать заказчику; контакт для доступов не указан). Commit и push — пользователь или агент только по его явному указанию. Состояние: корень опубликован коммитом `2fb9487`, у `legacy-landing/github-pages/` своего `.git` нет.

### D-15

**Почта.** SMTP почтового ящика домена или транзакционный сервис на аккаунте владельца; From — адрес домена, Reply-To — клиент. Перед рабочим подключением проверить MX/SPF/DKIM/DMARC; почтовые DNS-записи не менять. Почему: неизвестно, как обслуживается почта aiqme.com.

### D-16

**Демо-сборка** (18.10, вместе с R-041). Готовая статическая сборка хранится в отслеживаемой папке `aiqme-site/demo/` и открывается по адресу https://greatgleb.github.io/3d-fabrication-web/aiqme-site/demo/ — как прежний лендинг из `legacy-landing/github-pages/` (Pages раздаёт корень ветки `main`, корневой `.nojekyll`); отдельный репозиторий не нужен. В папке — только статическая сборка без секретов и данных заказчика. Сборка W-24 от решения не зависит; публикация (commit и push папки) — по разрешению пользователя.

### D-17

**Агент ночного прогона.** Boost в `aiqme-site/` настраивается на оба агента (`codex`, `claude_code`); их MCP-конфигурации содержат локальные абсолютные пути и исключены корневым `.gitignore`; правила tasks.json говорят о «сессии агента», правила Boost, мешающие автономной работе, уточнены в `rules`. Почему: прогон запускается то из Claude Code (читает `CLAUDE.md`, `.mcp.json`), то из Codex, а план и эксперимент написаны под Codex (`boost.json`: `agents: ["codex"]`, `.codex/config.toml`) — план обязан работать под обоими. Альтернатива «только один агент» отклонена пользователем.

### D-18

**Контрольные точки.** Коммитов нет: после зелёного `bin/check` агент сохраняет архив `aiqme-site/build/checkpoints/W-xx.tar.gz` (без `vendor/`, `node_modules/`, `storage/`, `build/`); `build/` игнорируется Git. Почему: commit без указания пользователя запрещён, и без точек откат сломанного задачей N результата N−1 — только вручную. Альтернатива — локальные коммиты в отдельной ветке (например, `overnight/aiqme-site`) после зелёного `bin/check` и проверки `git status`/`git ls-files` на приватные пути; push запрещён в любом случае.

### D-19

**Тексты и CSS прототипа в публичном репозитории.** Тексты страниц и CSS для публичного сайта заказчика класть можно (W-03 — CSS в `resources/css/prototype/`, W-04 — тексты в сидер, W-24 — в демо). Нельзя: медиа третьих лиц (ролики, фото, логотипы брендов), демо-данные с персональной информацией, кадры и DOM из `evidence/`, архив исходников прототипа — только заглушки и ссылки. DOM из `evidence/` можно читать как источник текстов (W-04): в репозиторий попадают только извлечённые тексты, не разметка и не файлы `dom.html`. Почему: исходники и аудит прототипа исключены `.gitignore`, а тексты и CSS всё равно будут опубликованы на сайте. Альтернатива — сидер-тексты в игнорируемом файле, подключаемом локально.

### D-20

**Сетевой доступ на уровне L.** Разрешены только загрузки пакетов и образов для версий, указанных в плане или в `composer.lock`/`package-lock.json`: Packagist (метаданные), dist-архивы Composer с GitHub (`api.github.com`, `codeload.github.com` — только чтение; так скачиваются пакеты `composer.lock` эксперимента и `google/auth` для W-18), npm, Docker Hub и штатные apt-репозитории базового образа (`deb.debian.org`) — только внутри `docker build` образа W-20 (расширения intl, pdo_pgsql, gd, zip, bcmath). Запрещены запросы к Stripe, Google, Telegram, внешним SMTP-серверам (локальный Mailpit из dev-compose разрешён) и любые записи во внешние системы. Boost `search-docs` обращается к `boost.laravel.com` и не используется — документация читается из `vendor/`. Если сеть недоступна — задача блокируется с записью в `progress.md`. Почему: правило «не вызывать внешние сервисы на уровне L» буквально запрещало и реестры, без которых не выполнить W-01 (`composer create-project`/`install`, npm, Vite), W-20 (образа `php:8.4-fpm` локально нет) и Lighthouse (`npx lighthouse@<версия>`). Альтернатива — запретить сеть полностью и заранее подготовить кэш Composer/npm и образ.

### D-22

**VAT в подтверждённой цене.** Подтверждённая цена и все платёжные запросы — суммы с VAT; счёт выделяет VAT из каждой строки (правило округления — §3.5), итог счёта = подтверждённая цена; продавец не плательщик — VAT 0 с пометкой из настроек. Почему: план не говорил, брутто или нетто цена администратора и клиента, а при VAT «сверху» итог счёта разошёлся бы с оплатой. Альтернатива — цены без VAT и VAT сверху, тогда платёжные запросы считаются от суммы с VAT.

### D-23

**Адрес покупателя в счёте.** Адрес берётся из заявки или профиля, если он есть, иначе счёт выпускается без адреса покупателя; подтверждается вместе с D-04/D-05 до рабочего выпуска счетов. Почему: при самовывозе адрес физлица не запрашивается (§1.2).

### D-24

**Габарит оборудования.** Одно число 250 мм (лимит FDM прототипа; материалы ядра — FDM) с пометкой «не подтверждено» в админке; с ним сравнивается каждый размер модели после единиц и масштаба; превышение — предупреждение, не блокировка. Настройка 10–2000 мм. Почему: калькулятору W-11 нужно значение по умолчанию, а D-09 его не задавал.

### D-25

**Логотип.** Логотип прежнего сайта заказчика `legacy-landing/site/assets/images/logo-dark.png` и `logo-light.png` копируется в `aiqme-site/` (`legacy-landing/` не меняется). Почему: логотип прототипа (`/assets/logo.jpg`) — файл прототипа, его не копируем. Альтернатива — текстовый логотип до получения файла от заказчика.

**Лента статей на главной.** Выводит только опубликованные статьи раздела «новости»; пока их нет — заглушка без ленты (§7.3); статьи библиотеки на главной не выводятся. Почему: прототип показывает 3 статьи библиотеки, а план — заглушку новостей. Альтернатива — как в прототипе, 3 последние статьи библиотеки.

**Тексты политик.** На уровне L ничего не меняется (черновики-заглушки D-11); условие W-23 — опубликованы реальные тексты политик конфиденциальности, cookie, доставки и возвратов. Почему: сайт собирает персональные данные (формы, аккаунты, заказы).

### D-28

**Режим запуска сессии ночного агента.** Codex — `codex exec --sandbox danger-full-access` ([run/codex-command.md](run/codex-command.md)). Claude Code — `claude -p --permission-mode dontAsk` из корня репозитория с правилами [run/claude-settings.local.json](run/claude-settings.local.json): файл кладётся в `.claude/settings.local.json` корня (исключён строкой `/.claude/settings.local.json` корневого `.gitignore`); в нём же allow-правило `Bash(bash docs/planning/edition-2/run/preflight.sh)` (подтверждено пользователем 19.10) — без него предпроверка W-01 в `dontAsk` отклоняется; Boost MCP — флагом `--mcp-config aiqme-site/.mcp.json` только в сессиях после W-01, когда файл есть. Сессия — под учётной записью или в окружении без ключей и токенов push к GitHub; изоляция при доступе к Docker — [D-39](#d-39). Первый шаг W-01 — `bash docs/planning/edition-2/run/preflight.sh` ([run/preflight.sh](run/preflight.sh)): скрипт сам дописывает результат в `aiqme-site/docs/progress.md` (без перенаправления, иначе правило не совпадёт), при FAIL прогон останавливается. Список правил не уже команд задач и D-18 (`docs/requirements.md` — для W-21). Ограничения D-20 и `rules` действуют в любом режиме. Почему: `codex exec` по умолчанию работает в песочнице только для чтения, а без сети, Docker и записи в кэши (`~/.npm`, `~/.cache/composer`, `~/.cache/ms-playwright`) блокируется W-01 и за ней весь прогон; план должен выполняться под обоими агентами (D-17).

Особенности Claude Code (сверено 19.10 с code.claude.com/docs: CLI reference, permissions, permission-modes; перед первым запуском сверить с `--help` установленных версий):

- В `dontAsk` без запроса идут только чтение файлов в рабочих каталогах (из корня — `docs/` и эксперимент) и разрешённые правила; `ls`, `cat`, `grep`, `find`, `which` и читающие формы `git` проходят без правил. Правила можно задать и `--allowedTools`/`--disallowedTools`; правила `.claude/settings.json` в `claude -p` без доверия к каталогу не применяются; глобальный excludes пользователя под отдельной учётной записью не действует (поэтому строка в корневом `.gitignore`).
- `/путь` в правилах отсчитывается от основного рабочего каталога, а в файле `--settings <файл>` — от каталога файла (там нужны абсолютные `//путь`). Правило `Edit` действует и на Write, и на перенаправления `>`/`tee`; правила `Write(путь)` не проверяются.
- Правилом не одобряются и в `dontAsk` отклоняются: `./bin/check` при одном `Bash(bin/*)` (поэтому разрешены три формы, после `cd aiqme-site`), `find` с `-exec`/`-delete`, команда с присваиванием переменной впереди (`NODE_BINARY=… bin/check` — переменные в `.env` или скрипте), `cd` вместе с `git` (`git` — из корня с путём), `cd` вместе с перенаправлением (`cd aiqme-site && bin/check > build/check.log`), `printf` с конвейером (D-29). Composer — `bin/php /usr/local/bin/composer …`; `aiqme-site/experiments/lunar-aiqme/bin/php` — только `-m` предпроверки и `create-project` в W-01, пока своего `bin/php` нет (эксперимент только читается).
- `ssh -T -o BatchMode=yes -o StrictHostKeyChecking=accept-new git@github.com` и `gh auth status`, если агент выполняет их сам, — ровно в этом виде, без `2>&1` и других перенаправлений, иначе правило не совпадёт; внутри `run/preflight.sh` это ограничение не действует (правило сверяется с командой запуска скрипта).
- `.mcp.json` и каталог `.claude/` — защищённые пути: их запись инструментами Edit/Write в `dontAsk` отклоняется, и `permissions.allow` (в том числе `Edit(/aiqme-site/**)`) её не открывает («Protected paths»). Поэтому `aiqme-site/.mcp.json` создаётся и исправляется только командой (`boost:install` через `bin/php`) или скриптом через `python3`; неудача записывается в `progress.md` и задачу не блокирует (W-01). `mcp__laravel-boost__*` действует, только если Boost MCP подключён; без него задачи выполнимы (`rules`).
- Node и npm стоят через nvm: PATH сессии должен их включать (`which node npm` — в предпроверке, §9.1), иначе вызов по абсолютному пути не совпадёт с `Bash(npm *)`/`Bash(node *)`.
- deny `WebFetch`/`WebSearch` — запрет, а не отсутствие разрешения: часть доменов документации WebFetch открывает без подтверждения в любом режиме (D-20; документация — из `vendor/`). deny `Read(/legacy-landing/instance/**)` нужен, потому что из корня чтение иначе идёт без правил; deny `Bash(python3 docs/customer-prototype/tools/*)` — CDP к Chrome пользователя (D-30).
- Allowlist — условная граница, а не защита: `rm`/`mv`/`cp` не ограничены путями, `npx`, `docker exec`, `python3` выполняют любые команды. Защиту дают учётная запись без ключей push и изоляция от файлов пользователя: группа docker равнозначна root на хосте (`docker run -v /home/…:/h` читает `~/.ssh`, `gh`, профиль Chrome и `instance/` в обход deny), поэтому при `Bash(docker *)` — D-39.

Альтернативы: для Codex — `--sandbox workspace-write` с разрешённой сетью, прогретыми кэшами Composer/npm и проверенным доступом к Docker; для обоих агентов — режим без запросов разрешений только в изолированном контейнере или ВМ без ключей push (выбор пользователя).

### D-29

**Пароль администратора без терминала.** Без терминала `aiqme:make-admin` читает одну строку из stdin по флагу `--password-stdin` (пароль не попадает в argv и историю); в терминале — скрытый ввод Laravel Prompts; опции со значением пароля нет. `bin/browser-check` создаёт администратора и клиента в своей БД `aiqme_browser` со случайным паролем на каждый запуск (W-03); в W-20 `bin/browser-check --base-url …` передаёт случайный пароль в stdin подпроцесса `docker compose -f docker-compose.prod.yml exec -T -u www-data app php artisan aiqme:make-admin --password-stdin` (`printf` с конвейером в `dontAsk` не разрешён, D-28). Почему: у `codex exec`, `claude -p` и `docker compose exec -T` терминала нет, и браузерные проверки админки, кабинета и `/ru/` (W-03, W-08, W-14, W-21) и сценарий prod-compose W-20 не смогли бы создать администратора, а обходы (опция с паролем, сидер с известным паролем, `tinker`) противоречат плану. Альтернатива — администратора создаёт только пользователь; тогда браузерные проверки админки и сценарий W-20 с действиями администратора — «ждёт проверки пользователем».

### D-30

**Удалённая отладка Chrome.** Агенту ночного прогона Chrome пользователя, CDP и `docs/customer-prototype/tools/` запрещены (`rules`, deny D-28; прототип — только сохранённые `evidence/`). Пользователь выключает удалённую отладку в `chrome://inspect/#remote-debugging` перед запуском (шаг 3 D-39). Предпроверка W-01 записывает предупреждение, если есть `~/.config/google-chrome/DevToolsActivePort`; при D-39 по умолчанию и (б) `~` — каталог учётной записи прогона, файла пользователя она не видит, поэтому записывается «не проверено (D-39)», а выключение остаётся обязательным шагом подготовки (порт CDP на 127.0.0.1 доступен любой локальной учётной записи). Почему: корневой `AGENTS.md` направляет к Chrome пользователя через CDP, а профиль содержит вошедшие сессии (GitHub, почта) — доступ по CDP обходил бы изоляцию «без ключей push» (D-28). Альтернатива — оставить отладку включённой, полагаясь только на запрет в `rules`; применима только при D-39 (в).

### D-31

**Шифрование внешней копии** (дополнение к D-13). Без дополнительного шифрования в MVP; копия лежит в хранилище владельца с доступом только у владельца; на сервере каталог копий 0700, файлы 0600 (W-29). Почему важно: в копии — персональные данные, STL заказов и счета. Альтернатива — шифрование ключом владельца (например, `age`) до выгрузки.

### D-32

**Блок «Команда» на «О нас».** Блок «The people behind the solutions» не выводится до получения реальных фото, имён и ролей (строка таблицы D-21; W-04, W-05). Почему: в прототипе вместо данных — заметка автора. Альтернатива — заголовок блока с нейтральным текстом без фото.

### D-33

**Способы оплаты.** `payment_method_types = ['card']` (кошельки Apple Pay и Google Pay — D-42), W-16. Почему: требование — оплата картой (R-015), а `automatic_payment_methods` эксперимента при включённых в Dashboard отложенных методах (SEPA Debit и т. п.) оставляет intent днями в `processing`, где отмена запроса не определена. ### D-34

**VAT для компании из другой страны ЕС.** Одна ставка для всех покупателей; бухгалтер подтверждает её вместе с D-05/D-22 до рабочего выпуска счетов (W-23). Обратное начисление (reverse charge) — отдельной задачей, только если его потребует бухгалтер. Почему: форма заявки принимает страну ЕС и VAT-код компании, а план считает одну ставку (D-05, D-22).

### D-35

**Общий обратный прокси** (уточняет D-01). Caddy; пример W-20 — для Caddy: без директивы `log` (журнала доступа нет, Referer с гостевым токеном не пишется), `request_body max_size 260MB`; доверенные прокси — §6.6. Почему: §8.1 рекомендует Caddy, а пример W-20 был в директивах nginx. Альтернатива — nginx-прокси с тем же `map $request_uri $loggable` и `client_max_body_size 260m`, что в `web`, и `proxy_read_timeout 120s` (§6.4, W-20).

### D-36

**Оговорка о представительстве брендов.** Фраза «Planned brands and solutions. This is not a claim of official representation.» под лентой брендов каталога удаляется вместе с другими плановыми пометками каталога (таблица D-21), как аналогичная фраза главной; вернуть можно правкой `ui_text`. Почему: прототип предлагает FDM/SLA/SLS/Metal, а план считает только FDM (D-09, D-24) и исключает технологии (§1.5). Альтернатива — кнопки технологии как пожелание без влияния на цену; тогда нужны списки материалов каждой технологии.

### D-38

**VAT в предварительной оценке.** Таблица шага 4 и сводка калькулятора VAT не упоминают (поле «PVM kodas (neprivaloma)» · «VAT number (optional)» шага 5 остаётся, §1.2); итог подписан «предварительная оценка; доставку и окончательную цену подтверждает администратор»; тарифы D-09 понимаются как брутто (§1.2, W-27). ### D-39

**Изоляция ночного прогона при доступе к Docker** (уточняет D-28). Прогон идёт под отдельной учётной записью `aiqme-run` без своих ключей GitHub, с rootless Docker (контейнеры видят только её файлы), в своей копии корня `/home/aiqme-run/3D_website`; домашний каталог пользователя ей закрыт (`/home/<пользователь>` — 0750). Подготовку (шаги 0–2, Ubuntu 24.04) выполняет пользователь — [run/prepare-aiqme-run.sh](run/prepare-aiqme-run.sh); возврат — [run/return-results.sh](run/return-results.sh); проверку — предпроверка W-01 ([run/preflight.sh](run/preflight.sh)). Почему: группа docker равнозначна root на хосте — `docker run -v /home/<пользователь>:/h …` читает `~/.ssh`, токен `gh`, профиль Chrome и `legacy-landing/instance/` любой учётной записи в обход deny D-28, а клон с GitHub не подходит: в нём нет игнорируемых входов задач (незакоммиченный план, `docs/customer-prototype/{audit-20261016,evidence,source-backup-20261016}/`, `runtime/` и `app/vendor/` эксперимента) — без них W-01 не соберёт `bin/php`, а тексты по `rules` заменились бы нейтральными надписями.

- **Подготовка, шаги 0–2** ([run/prepare-aiqme-run.sh](run/prepare-aiqme-run.sh), там же причины каждой команды): учётная запись, linger и rootless Docker — всё «под `aiqme-run`» только в сессии `sudo machinectl shell aiqme-run@` (под `sudo -iu` rootless Docker не стартует); копия корня без `legacy-landing/instance/`, `legacy-landing/archive/`, `docs/customer/`, `docs/planning/run/` и `.env*`; (1а) пути `.so` в `runtime/conf/*.ini` эксперимента переписаны на копию; nvm с Node 22, агент и его вход под `aiqme-run`, Python Playwright с Chromium в venv в PATH, `.claude/settings.local.json` копии из `run/`.
- **Шаг 3** (вручную) — удалённая отладка Chrome выключена (D-30, обязательно). Локальные сервисы других проектов пользователя (базы, Redis, dev-серверы на `127.0.0.1` и `0.0.0.0`) учётной записи прогона доступны по сети — D-39 изолирует файлы, а не порты; риск принят пользователем 19.10 (альтернатива — остановить эти сервисы на время прогона). Агент запускается из этой сессии в `/home/aiqme-run/3D_website` по D-28.
- **Несколько ночей:** копию готовят один раз; между ночами — только возврат; повторная подготовка (шаги 1 и 1а) — только после возврата, иначе `rsync` затрёт несданные файлы агента.
- **Возврат** ([run/return-results.sh](run/return-results.sh)) — только `aiqme-site/` с `--delete`, без `experiments/`, `vendor/`, `node_modules/` и файлов с путями `aiqme-run` (`.env*`, `.mcp.json`, `.codex/`, `public/storage` — у себя их создают заново). Своих незакоммиченных файлов в `<корень>/aiqme-site/` до возврата не держат. `docs/requirements.md` целиком не копируется (затёр бы правки пользователя): только после W-21 — `diff -u` и ручной перенос строки «Новый сайт». Затем `git status`/`git diff` до commit.
- **W-22** (уровень T, с пользователем) по умолчанию идёт в той же копии под `aiqme-run` (тестовые ключи — в `.env` копии); если её ведут в корне пользователя — сначала `composer install`, `npm ci`, `.env` из `.env.example` и `key:generate`, `storage:link`, dev-compose, `migrate`, `aiqme:bootstrap`.
- **Предпроверка W-01** ([run/preflight.sh](run/preflight.sh)): Docker rootless; входы задач есть; в `legacy-landing` нет `instance` и `archive`; PHP эксперимента в копии с расширениями (иначе не выполнен шаг 1а); Python Playwright импортируется. При нарушении прогон останавливается с записью в `progress.md`.
- **Выбор альтернативы:** до запуска пользователь записывает в `aiqme-site/docs/progress.md` копии, где идёт прогон, отдельной строкой без маркера списка `D-39: вариант б` или `D-39: вариант в`; агент читает только её, без строки — вариант по умолчанию, обе строки сразу — FAIL предпроверки. (б) ВМ или контейнер без доступа к домашнему каталогу пользователя с той же копией (подготовка и возврат те же, в шаге 1а — путь копии в ВМ) — снимается требование `rootless`. (в) Принять риск: прогон в корне пользователя (шаги 1, 1а и возврат не нужны), ключ GitHub защищён парольной фразой, на время прогона выполнен выход из `gh` и закрыт ssh-agent — снимаются `rootless` и проверка отсутствия `instance/` и `archive/` (deny D-28 остаётся). Остальные пункты предпроверки действуют при любом варианте.
