# 2. Архитектура на Laravel + Lunar

[← План](README.md). Основание: [сравнение Lunar](../../research/lunar-vs-laravel-comparison-20261017.md), код [prototypes/lunar-aiqme](../../../aiqme-site/experiments/lunar-aiqme/README.md) и [orders-comparison/shared](../../../aiqme-site/experiments/orders-comparison/README.md). Пометка **Рекомендация** означает выбор разработчика плана для неутверждённой части; его можно изменить без пересмотра остальной архитектуры.

## 2.1. Стек и версии

| Компонент | Версия | Источник |
|---|---|---|
| PHP | 8.4 (локально 8.4.24 + изолированные расширения эксперимента) | `prototypes/lunar-aiqme/bin/php` |
| Laravel | 13.37.0 | `prototypes/lunar-aiqme/app/composer.lock` |
| Lunar core/admin, `lunarphp/stripe` | 1.5.0 | там же; штатный Stripe-драйвер для второго платежа не используется |
| Livewire | 3.8.10 | там же |
| Filament | 4.15.2 (зависимость панели Lunar) | там же |
| Stripe PHP SDK | 16.6.0 | там же |
| Уже в дереве зависимостей Lunar | spatie/laravel-medialibrary 11.23.9, spatie/laravel-activitylog 4.12.3, barryvdh/laravel-dompdf 3.1.2 (dompdf 3.1.6), laravel/scout 10.25.0 | используем вместо новых пакетов |
| Laravel Boost (dev) | 2.10.3, агент Codex | `boost.json`, проектный `.codex/config.toml` |
| БД | PostgreSQL 17 в эксперименте; в рабочей среде — **Рекомендация** PostgreSQL 17 (D-02) | эксперимент |
| Фронтенд | Blade + Livewire; Vite; JS-модули калькулятора, просмотра STL (three.js STLLoader из `tools/stl/`), видео и лент | `site/assets/`, V2 |

Перед изменением любой версии — проверка совместимости и полный набор тестов. Новые пакеты добавляются только при доказанной необходимости.

**Boost и Codex.** В эксперименте Boost 2.10.3 настроен на агента Codex: `boost.json` (`agents: ["codex"]`, guidelines и MCP включены) и проектный `.codex/config.toml`, который запускает `artisan boost:mcp` через изолированный `bin/php`. Глобальные настройки Codex и корневой `AGENTS.md` при этом не менялись. Для `aiqme-site/` повторяем ту же схему: Boost генерирует `aiqme-site/AGENTS.md` со своими правилами, корневой `AGENTS.md` не перезаписывается. Инструменты Boost (`search-docs`, `database-schema`, `browser-logs`) пригодны для сессий workflow. Два правила Boost уточняются заданием: «не менять зависимости без одобрения» — версии из этого плана считаются одобренными, новые пакеты требуют обоснования в `progress.md`; «документацию только по запросу» — запись `aiqme-site/docs/progress.md` и отчётов проверки входит в каждую задачу ([tasks.json](tasks.json), `rules`).

## 2.2. Граница торгового ядра и сервисов AIQME

| Lunar отвечает за | AIQME отвечает за |
|---|---|
| Корзина как конвейер создания заказа (`Cart::add/updateLine/remove/createOrder`), валидатор перед созданием заказа | Приём STL, оценка, порядковый номер, гостевой доступ |
| Заказ и строки заказа с суммами в центах EUR, клиенты (`Customer`) и адреса заказа | Подтверждение и изменение цены, история согласования, состояние производства |
| Транзакции (`lunar_transactions`) как учёт поступивших денег и возвратов | Платёжные запросы (аванс, остаток), Stripe-адаптер, webhook, сверка |
| Валюта EUR, налоговые классы (**нулевая ставка**, чтобы Lunar не добавлял демо-НДС; налоги считает счёт AIQME) | Счета: реквизиты, VAT, нумерация, PDF |
| — | Весь контент, включая товары и бренды каталога; переводы; публикация; Telegram; Sheets; почта |

**Каталог.** Товары, бренды и категории хранятся в контентной модели AIQME, а не в каталоге Lunar. Обоснование: им нужна публикация по каждому языку (В-017), одинаковые редакторы в вебе и Telegram и заглушка по умолчанию, а продажа не утверждена (D-12). Каталог Lunar публикуется одним статусом на все языки и требует вариантов, цен и налоговых классов. Если продажу позже включат, карточку свяжут с вариантом Lunar отдельной задачей.

Lunar не форкается, `vendor/` не редактируется. Используются только документированные точки расширения: `Purchasable`, валидаторы корзины, генератор номера заказа, транзакции.

## 2.3. Роль штатной панели Lunar

Обязательная админка одна — собственная, в оформлении прототипа (Blade/Livewire). Штатная Filament-панель Lunar регистрируется **только в локальной среде** (флаг `AIQME_LUNAR_PANEL=true`, по умолчанию выключен). Это служебный инструмент разработчика для просмотра моделей Lunar. В рабочей среде маршрута `/lunar` нет: штатные действия панели (смена статуса, правка транзакций) обходили бы правила заказа. Расширение `ManufacturingOrderExtension` из эксперимента не переносится. Модель `Staff` не нужна: администратор — `User` с флагом `is_admin`.

## 2.4. Модули приложения

Новое приложение — каталог `aiqme-site/` в корне рабочего пространства; соседний `aiqme-site/experiments/` — эталонные эксперименты, в приложение не входят. Отдельного Git внутри `aiqme-site/` нет: весь корень публикуется в публичный репозиторий `GreatGleb/3d-fabrication-web` (приватное исключено корневым `.gitignore`; секреты в Git не попадают). Сборка прежнего лендинга `legacy-landing/github-pages/` хранится в том же репозитории и раздаётся Pages из папки. Удалённый репозиторий — D-14. Push без разрешения запрещён.

```
aiqme-site/app/
  Domain/Orders/      OrderSubmission, OrderWorkflow, ProductionStage, PriceRevision, OrderNumber
  Domain/Pricing/     StlAnalyzer (PHP), EstimateService, CalculatorSettings
  Domain/Payments/    PaymentRequestService, StripeInstallments, StripeWebhookHandler, Reconciliation
  Domain/Invoices/    InvoiceService, InvoiceNumberer, SellerSettings, InvoicePdf
  Domain/Content/     ContentService, ContentTypes, Publication, Placeholders, UiTexts, MediaService
  Domain/Forms/       ContactRequest, TrainingRegistration
  Domain/Integrations/ IntegrationEvents (outbox), SheetsProjector, Mailer, TelegramBot
  Domain/Audit/       AuditLog (поверх spatie/activitylog)
  Http/               публичные контроллеры, кабинет, админка (Livewire), webhook-и
```

Правило: контроллер, Livewire-компонент, обработчик Telegram и консольная команда вызывают **один и тот же сервис** и не содержат бизнес-правил. Права проверяются в сервисе (единственный администратор — `Gate::define('admin')`; клиент — владелец объекта; гость — секретный токен заказа).

## 2.5. Данные (новые таблицы AIQME)

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `users` (+`is_admin`), Lunar `customers` | Клиент и администратор | Саморегистрация не ставит `is_admin`; администратора создаёт команда `aiqme:make-admin` |
| `stl_files` | Приватный STL: владелец (user или гостевой заказ), путь, исходное имя, размер, sha256, результат анализа (объём, габариты, треугольники, версия анализатора) | Путь назначает сервер; файл вне `public/` |
| `stl_parts` | `Purchasable` строки заказа: ссылка на `stl_files`, параметры, пожелания, оценка | Как `StlPart` эксперимента |
| `order_meta` | Номер заказа, гостевой токен (хеш), снимок настроек калькулятора, контакты, способ получения | Номер уникален; токен хранится только как хеш |
| `production_states` | Стадия, `confirmed_at`, `started_at`, ревизия цены | Изменения цены запрещены после `started_at` |
| `price_revisions` | Было/стало по строкам, основание и ссылка на согласование, автор | Уникально `(order_id, revision)` |
| `payment_requests` | Сумма, валюта, состояние (`pending/paid/void/needs_review`), `stripe_intent_id`, idempotency key | Сумма ≤ неоплаченный остаток минус другие открытые запросы |
| `payment_events` | Входящие события Stripe: `event_id` PK, digest, результат обработки | Повтор события — без эффекта |
| `order_messages` | Сообщение администратора и ответ клиента | Ответ ничего не меняет автоматически |
| `invoices`, `invoice_lines` | Номер, серия, вид, снимок реквизитов продавца и покупателя, суммы, VAT, путь PDF | Уникально `(series, number)`; уникально основание выпуска |
| `content_items`, `content_translations`, `content_revisions`, `ui_texts` | Контент всех типов; перевод на локаль со своим slug, полями, SEO, `published_at`, `revision`; прежние версии | Уникально `(locale, type, slug)`; сохранение с устаревшей ревизией отклоняется |
| `contact_requests`, `training_registrations` | Заявки форм и вложения | — |
| `integration_events` | Outbox для Sheets и почты: тип, сущность, данные, статус, попытки, последняя ошибка | Пишется в той же транзакции, что и изменение |
| `telegram_bindings`, `telegram_dialogs`, `telegram_updates` | Привязанный chat id администратора, состояние диалога, дедупликация `update_id` | Один привязанный чат |
| `settings` | Реквизиты продавца, VAT, нумерация, ссылка на таблицу, настройки калькулятора (версионный снимок) | Секреты сюда не пишутся — только в `.env` |

Деньги — целые центы EUR. Время — UTC, вывод в часовом поясе `Europe/Vilnius`. Удаление аккаунта не каскадирует на заказы, платежи и счета.

## 2.6. Что переносится из эксперимента и с какими исправлениями

Код эксперимента — проверенная наработка, а не готовый production-код. Переносим осознанно, с перечисленными исправлениями и тестами.

| Наработка | Переносим | Обязательные изменения |
|---|---|---|
| `OrderWorkflow` (подтверждение цены, запрос оплаты, приём квитанции, производство, отмена, баланс) | Правила и проверки | (1) Отмена при открытом платёжном запросе: сначала отменить запрос (`void` + отмена PaymentIntent в Stripe после commit), а не вечная блокировка. (2) Поздняя оплата отменённого заказа и переплата **записываются** как транзакция с пометкой «на сверку», webhook отвечает 200. В эксперименте здесь исключение и откат, из-за чего Stripe повторял бы событие бесконечно. (3) Добавить стадии производства (§3.4). (4) `$fillable` вместо `$guarded = []` |
| `StripeInstallments` | Два автоматически списываемых PaymentIntent, сумма из `PaymentRequest`, metadata, idempotency key на запрос, проверка webhook | **Сетевой вызов вне транзакции БД**: транзакция 1 — блокировка, проверка, сохранение ключа; вызов Stripe с таймаутом и тем же ключом; транзакция 2 — сохранение `intent_id`. При неизвестном исходе повтор с тем же ключом или чтение intent, а не новый intent. Разрешить live-режим только в рабочей среде по конфигурации; test/live ключи и секреты webhook раздельны |
| `BasketService`, `RequestCartValidator`, `StlPart` | Корзина Lunar → заказ без платёжного адреса | Поддержка гостя (корзина без `user_id`, владелец файлов — заявка). Цена строки — серверная оценка `EstimateService`, а не фиксированные 50/70 EUR из `StlIntake::unit` |
| `StlIntake` | Хранение с sha256, удаление файла при ошибке | Реальная проверка структуры STL в PHP (`StlAnalyzer`), лимиты из настроек; запись файла и строки согласованы — нет «сирот» |
| `ContentPublisher` | Проверка ревизии при сохранении | Полная контентная модель (§4) |
| `LocalTestAdapter`, `comparison:demo`, фикстуры `buyer@/admin@example.test`, пароль `local-probe-only`, `.env` эксперимента | **Не переносятся**. Локальные квитанции — только в тестах | — |
| UI эксперимента (`shared/views`) | Не переносится | Интерфейс — по прототипу заказчика |
| 38 общих тестов | Переносятся как основа набора тестов с адаптацией к новым именам | Плюс тесты на исправления выше |

## 2.7. Фоновое выполнение и повторы

**Рекомендация** (D-03): очередь Laravel с драйвером `database`, один процесс `queue:work` под supervisor/systemd или в контейнере, планировщик `schedule:run` раз в минуту. Redis не добавляем: нагрузка небольшая (В-060).

- Внешние вызовы (почта, Sheets, Telegram-ответы, Stripe) никогда не выполняются внутри транзакции БД.
- События для Sheets и почты пишутся в `integration_events` в той же транзакции, что и изменение; задание ставится `afterCommit`. Планировщик раз в 5 минут подбирает события без успешной доставки — это защита от потерянной постановки в очередь.
- Повторы: `tries`/`backoff` с нарастанием; ошибки видны в Overview админки. Сбой почты или Sheets не откатывает заказ, оплату или правку.
- Webhook Stripe и Telegram отвечают 2xx только после сохранения события; повтор события обрабатывается без эффекта.

## 2.8. Размещение рядом с другими сайтами

Подробно — [§8](08-operations.md). Приложение не делает предположений о соседях: отдельная БД и пользователь БД, отдельный `.env` и `APP_KEY`, отдельные каталоги хранения и логов, свой процесс очереди и cron, свой домен. Никаких общих с другими проектами секретов, сессий или кэша.
