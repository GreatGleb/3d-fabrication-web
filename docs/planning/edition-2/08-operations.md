# 8. Эксплуатация

[← План](README.md). Сервер ещё не арендован. На нём будут несколько сайтов, включая другой более крупный проект. Хостинг, окончательная БД и способ фонового выполнения не утверждены. Ниже — рекомендации, явно помеченные; нагрузку другого проекта не придумываем.

## 8.1. Размещение (D-01, рекомендация)

- VPS в ЕС (рынок — Литва), Ubuntu LTS.
- Каждый проект — отдельный **Docker Compose** проект: собственные контейнеры, сеть, тома, `.env`, пользователь и БД. AIQME: `app` (PHP-FPM 8.4), `web` (nginx), `worker` (`queue:work`), `scheduler` (`schedule:run`), `db` (PostgreSQL 17), собственный том `storage` (в `app`, `worker`, `scheduler`; в `web` — только для чтения: nginx раздаёт публичные медиа `/storage/…` через симлинку `public/storage` внутри образа, W-20). `worker` и `scheduler` работают от `www-data`, artisan в `exec` — с `-u www-data`.
- Один общий обратный прокси на хосте (по умолчанию Caddy с автоматическим TLS, D-35, или уже выбранный для крупного проекта) маршрутизирует домены по сетям проектов. У прокси нет доступа к данным проектов. Опубликованный порт Docker открывается в обход UFW, поэтому у `db`, `app`, `worker` и `scheduler` нет `ports:`, а `web` подключён только к внешней сети общего прокси (или опубликован на `127.0.0.1:<порт>`; тогда доверенный прокси приложения — шлюз сети проекта, §6.6).
- Лимиты CPU и памяти на контейнеры AIQME, чтобы один проект не вытеснял другие: `deploy.resources.limits` (`memory`, `cpus`) из `.env` со значениями по умолчанию (W-20); рекомендуемые значения — по измерению W-29.
- Compose вместо общих PHP-FPM и PostgreSQL хоста: одинаковая среда локально и на сервере, изоляция процессов и секретов. Если крупный проект уже использует общий PostgreSQL, допустим общий кластер с отдельной БД и ролью AIQME (D-02).

## 8.2. Размер сервера

Считается по сумме нагрузок, а не только AIQME. Для AIQME задача W-29 **измеряет** локально: память PHP-FPM под нагрузкой страниц, пик памяти серверного анализа STL на 25 МиБ / 500 000 треугольников, генерацию PDF, PostgreSQL в простое, рост диска (STL заказов: ориентир по старому плану — около 1,5 ГиБ за 30 дней при 10 файлах по 5 МиБ в сутки; это арифметика гипотезы, не измерение). Итог — строка «AIQME требует ≈ X ГБ RAM, Y vCPU, Z ГБ диска + рост», которую складывают с требованиями других проектов. Бюджет 10 USD/мес — старый предварительный ориентир для одного AIQME, не бюджет общего сервера.

## 8.3. Развёртывание

- Исходники — каталог `aiqme-site/` в публичном Git-репозитории корня `GreatGleb/3d-fabrication-web` (D-14; приватное исключено `.gitignore`, секреты — только в `.env` на сервере). Деплой: `git archive` нужной версии каталога `aiqme-site/` без `experiments/` на сервер → `docker compose build` (Dockerfile W-20 сам создаёт `bootstrap/cache` и каталоги `storage/`, собирает Vite в Node-стадии: в Git этих файлов нет; локально тот же контекст даёт `bin/build-context` из отслеживаемых и неигнорируемых файлов) → `php artisan migrate --force` (artisan здесь и ниже — `docker compose exec -T -u www-data app php artisan …`) → `php artisan aiqme:bootstrap` (идемпотентно: базовые данные Lunar, W-12) → `optimize` → перезапуск `worker`. При первом развёртывании на пустой БД один раз запускается сидер исходного контента W-04 по имени класса (на непустой БД он ничего не перезаписывает; тестовых пользователей `DatabaseSeeder` не содержит) и `aiqme:make-admin` (`docker compose exec -T -u www-data app php artisan aiqme:make-admin --password-stdin`, пароль из stdin, D-29); при обновлениях `make-admin` не запускается — он меняет пароль существующего администратора (только при явной смене пароля). На сервер не попадают `legacy-landing/` (включая `instance/`), `docs/` (переписка и материалы заказчика), `aiqme-site/experiments/` и тестовые фикстуры.
- Миграции — только совместимые вперёд. Откат кода не откатывает схему; после реальных заказов старую БД поверх новых данных не восстанавливаем.
- `.env` создаётся на сервере по шаблону `.env.example` без значений; в Git его нет. Во все PHP-сервисы (`app`, `worker`, `scheduler`) он монтируется только для чтения в каталог приложения, путь — `${AIQME_ENV_FILE:-./.env}`; `env_file` не используется: FPM с `clear_env = yes` не передаёт переменные рабочим процессам (W-20).
  - Локальный prod-compose W-20: игнорируемый `aiqme-site/build/prod-local/.env` (значения для HTTP на `127.0.0.1`, права 0644 — W-20) и своё имя проекта `name: aiqme-prod` в `docker-compose.prod.yml`, поэтому dev-`.env`, контейнеры и тома W-01 не затрагиваются; команды — `docker compose --env-file build/prod-local/.env -f docker-compose.prod.yml …` (иначе подстановка `${…}` возьмёт dev-`.env`).
  - Сервер: монтирование сохраняет владельца и права файла хоста, поэтому `.env` — `chown root:33 .env && chmod 0640 .env` (группа `www-data` образа; при 0600 PHP-FPM его не прочитает; runbook W-29). Отсюда команды `docker compose` (подстановка `${…}` читает `./.env`) и cron `bin/backup` — от `root` (`sudo`, crontab root); `bin/backup` при нечитаемом `.env` завершается с явной ошибкой.
- Перед первым запуском на aiqme.com: выписать текущие DNS-записи (A/AAAA/CNAME, MX, SPF/DKIM/DMARC, верификации, CAA), менять только веб-записи, не трогать почту info@aiqme.com. Сначала проверка на временном поддомене или IP, затем переключение.
- Stripe webhook endpoint (`/webhooks/stripe`, три события §5.5, версия API `2025-02-24.acacia`) регистрируется на рабочем домене до приёма первых оплат; Telegram webhook — командой `aiqme:telegram-webhook` после выпуска TLS (§5.4).
- Существующая статическая V2 на GitHub Pages (`legacy-landing/github-pages/`, https://greatgleb.github.io/3d-fabrication-web/legacy-landing/github-pages/) остаётся демонстрацией прежнего лендинга; рабочую коммерческую платформу там не размещаем (ограничение GitHub Pages). Демо нового сайта — отдельно, §8.7.

## 8.4. Фоновые задания

D-03, рекомендация: очередь `database`, один `worker` (очереди `default`, `sheets`, `mail`), `scheduler` раз в минуту. Задания планировщика: повтор недоставленных каналов `integration_events` (каждые 5 минут, W-09), ночная проверка файлов-сирот без удаления и очистка устаревших сессий и токенов сброса (W-29), ежедневное задание «ожидающие счета» (W-17). Ночную резервную копию запускает cron хоста через `bin/backup`: `pg_dump` 17 есть только в контейнере `db` (W-29). Наблюдение — Overview админки (неудачные задания, события «на сверку», давность последней копии по метке, которую пишет `bin/backup`, — W-29) и бесплатная внешняя проверка доступности `/up` (например UptimeRobot на аккаунте владельца — уровень P).

## 8.5. Резервные копии и восстановление

- **Рекомендация** (D-13): ежедневно `pg_dump` + архив `storage/app/private` и медиа. Хранить 14 дневных и 8 недельных копий на сервере (недельная — последняя копия ISO-недели; лишние удаляет `bin/backup`, числа — из `.env`, W-29) и копию **вне сервера** в хранилище владельца. Место внешней копии, сроки хранения документов и копий не определены.
- Копия — единый комплект: дамп и файлы одного запуска (сначала дамп через `docker compose -f docker-compose.prod.yml exec -T db pg_dump`, затем файлы тома `storage` через контейнер, а не с диска хоста), с манифестом sha256. Проверка комплекта: у каждой ссылки на файл в дампе (`stl_files.sha256`, вложения, PDF счетов) есть байты с тем же хешем. Каталог копий 0700, файлы 0600; внешняя копия — без дополнительного шифрования в MVP (D-31).
- Восстановление (чек-лист): `php artisan down` (новые заявки и webhook не принимаются; Stripe повторит доставку событий) → остановить `worker` и `scheduler` → восстановить БД и файлы → сверить хеши → сверить платежи Stripe после времени копии (успешные списания, которых нет в БД, вносятся по событиям Stripe, а не заново) → проверить, что номер следующего счёта больше последнего выданного (учёт выпущенных PDF и Sheets) → сбросить сессии → запустить.
- Одна реальная проверка восстановления — в локальном prod-compose на синтетических данных: копия → `down -v` (только проект prod-compose `aiqme-prod`, §8.3) → восстановление на пустые тома → сверка хешей (W-29). Локальные копии — в игнорируемом `aiqme-site/build/backups/`, на сервере — вне каталога приложения (путь в `.env`); БД и `storage` prod-compose — именованные тома, не каталоги внутри `aiqme-site/`. Тестовое восстановление не получает рабочих ключей Stripe, почты, бота и Sheets.
- Цель простоя — желательно не больше часа, допустимы сутки (В-061); это цель, а не гарантия.

## 8.6. Поддержка

После запуска сбой сначала пытается устранить заказчик, затем звонит разработчику (В-064). Задача W-21 готовит короткую инструкцию: где смотреть ошибки, как перезапустить worker, как восстановить копию, как сменить ключи.

## 8.7. Демо-сборка для GitHub Pages (рекомендация)

Требование — [§1.6](01-scope.md#16-демо-сборка-для-github-pages), задача [W-24](tasks.md#w-24). Ниже — рекомендуемый механизм, не утверждённое решение.

- **Источник — то же приложение.** Artisan-команда `aiqme:demo-export` (обёртка `bin/demo-build`) поднимает приложение с `APP_ENV=demo` и отдельной временной БД, заполняет её `DemoSeeder` (заглушки и демо-заказы без реальных данных; медиа прототипа по умолчанию [D-43](decisions.md#d-43) — статические файлы, копируются в сборку) и через HTTP-ядро Laravel в процессе рендерит список маршрутов: публичные LT/EN со статусом 200 из [§4.6](04-content-seo.md#46-ожидаемые-статусы-адресов-прототипа), экраны входа, кабинета и админки от имени демо-пользователей (`Auth::login` внутри команды, без HTTP-маршрута — единственное исключение из запрета обходов аутентификации; условия отказа команды и их тест — [W-24](tasks.md#w-24) done[7]). БД — отдельная `aiqme_demo` в dev-PostgreSQL W-01, команда создаёт её перед сборкой и удаляет после (миграции Lunar проверены только на PostgreSQL 17; SQLite не используется). Отдельный SPA или копия шаблонов не нужны: расхождение с основным сайтом минимально. Готовые пакеты статического экспорта Laravel с Laravel 13 не проверялись; простая собственная команда по списку маршрутов предпочтительнее.
- **Постобработка.** Ссылки и ресурсы переписываются под базовый путь Pages (`/<репозиторий>/`), маршруты сохраняются как `…/index.html`; в каждую страницу добавляются баннер «ДЕМО» на языке страницы и `meta robots noindex`; CSRF-токены и серверные `action` форм заменяются атрибутом `data-demo-form`. Небольшой `demo.js` перехватывает отправку и действия кабинета/админки и показывает «демо: данные не сохраняются» без сетевых запросов. Калькулятор отправляет заявку `fetch`-запросом (W-12), поэтому `data-demo-form` ставится на его контейнер и `demo.js` перехватывает и эту отправку.
- **Livewire в демо не работает и не эмулируется.** Скрипт Livewire отдаётся маршрутом `/livewire/livewire.js`, а действия идут POST-запросами на `/livewire/update`, которых на Pages нет. Поэтому экраны кабинета и админки в демо — статические HTML-снимки: скрипт Livewire и атрибуты `wire:*` удаляются, кнопки и формы получают `data-demo-form`, и `demo.js` показывает демо-сообщение. Перехват Livewire не пишется.
- **Состав.** Разделов оплаты и счетов в демо нет (ни в кабинете, ни в админке) независимо от порядка задач: список маршрутов экспорта их не содержит, а их блоки в шаблонах кабинета и админки в демо-режиме (`APP_ENV=demo`) не выводятся — это делает задача, добавляющая блок (W-16 — оплата, в том числе кнопка оплаты на гостевой странице, W-17 — счета и предупреждение о реквизитах, W-28 — «платежи на сверку»), с тестом. W-21 пересобирает демо и повторяет проверки W-24. Добавлять ли их — отдельное решение пользователя. Поиск в демо показывает демо-сообщение (серверного поиска нет), `?category=…` отдаёт тот же статический список.
- **Калькулятор.** Используется тот же модуль ядра из W-10, он уже работает в браузере; серверный пересчёт (W-11) в демо не вызывается, итог помечается как ориентировочный.
- **Вывод и проверка.** Результат — `aiqme-site/demo/` (отслеживается Git: его раздаёт Pages; промежуточные файлы — в игнорируемом `aiqme-site/build/`). Проверки — по образцу `legacy-landing/scripts/check_github_pages_ui.py`: статусы страниц, отсутствие JS-ошибок и внешних запросов, пометка «ДЕМО» и `noindex` на каждой странице, поиск секретов и данных клиентов.
- **Публикация** — [D-16](decisions.md#d-16); базовый путь сборки — `/3d-fabrication-web/aiqme-site/demo/`. Commit и push — только с явного разрешения; GitHub Actions не обязателен.
