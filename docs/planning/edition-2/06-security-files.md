# 6. Безопасность и файлы

[← План](README.md). Главные риски: чужой доступ к заказам и файлам, ложное «оплачено», потеря принятого заказа, утечка секретов. Один администратор, без ролей и MFA (В-044, В-072), но обычная авторизация и права проверяются на сервере.

## 6.1. Субъекты и права

| Субъект | Может |
|---|---|
| Посетитель | Публичные страницы, формы, калькулятор, отправка заявки |
| Гость с секретной ссылкой | Только свой заказ: просмотр, оплата открытых запросов, скачивание своих STL и счетов, ответ администратору |
| Клиент | Свои заказы, модели, адреса, счета; ничего чужого |
| Администратор (`is_admin`) | Всё, включая `/ru/`; создаётся только командой `aiqme:make-admin` |
| Stripe, Telegram | Только свои webhook-маршруты с проверкой подлинности |

- Чужой или несуществующий объект — **404**, не 403: существование не раскрывается. Знание номера заказа, ID или имени файла доступа не даёт.
- Админка и `/ru/` без входа администратора — **404** для всех (гость и клиент), без редиректа на вход; администратор входит через обычную страницу входа кабинета.
- Права проверяются в сервисе, не только в маршруте; Livewire-действия админки повторно проверяют `admin`.
- Владелец заказа — только вошедший клиент (`auth()->check()`) при непустом `user_id` заказа, равном его id. У гостевого заказа (`user_id` = null) владельца нет, доступ гостя — только право в сессии (§6.2). Сравнение `order.user_id === auth()->id()` эксперимента без этой проверки не переносится (для гостевого заказа `null === null` у любого посетителя). Проверка прав на заказ одна (W-32), тесты прав идут и на гостевом заказе (§9.2 «Права»).
- Клиент никогда не передаёт `paid`, `owner`, `is_admin`, `published`, цену или сумму оплаты: FormRequest + `validated()`, `$fillable`.
- Email из формы не делает владельцем гостевого заказа; привязки гостевого заказа к аккаунту нет (D-10).

## 6.2. Гостевой доступ

- Токен — 32 случайных байта (base64url), в БД только SHA-256; URL `/lt/uzsakymas/<номер>/<токен>` · `/en/order/<номер>/<токен>`.
- Неверный токен — 404; ограничение частоты по IP (превышение — 429, W-15). Отправка заявки — honeypot и частота по IP (§3.1, W-12).
- Страница оплаты `/lt/apmokejimas/<public_id>` токена не содержит; `public_id` доступа не даёт. Открытие гостевой страницы по верному токену пишет в сессию право на заказ — пару «заказ + SHA-256 токена»; при каждой проверке хеш сверяется с текущим хешем заказа, поэтому после перевыпуска ссылки старое право не действует. Страницу оплаты и возврат после 3DS (`return_url` — та же страница) видят владелец, администратор или сессия с этим правом, остальные — 404. Скачивание гостем своих STL и счетов — по тому же праву в сессии; в адресах файлов токена нет.
- Открытый токен не хранится, скопировать ссылку нельзя: администратор перевыпускает её (старая перестаёт работать), новая показывается один раз с предупреждением (§3.3).
- Ссылка не попадает в Sheets и журналы:
  - журнал доступа nginx приложения (W-20) не пишет гостевые адреса, ссылку сброса пароля (токен в пути, маршрут W-07) и возврат на страницу оплаты (`payment_intent_client_secret` в query после 3DS): `map $request_uri $loggable` + `access_log … if=$loggable` для `/lt/uzsakymas/`, `/en/order/`, ссылки сброса и `/lt/apmokejimas/`, `/en/checkout/` (`access_log off` внутри `location` не действует, когда запрос через `try_files` завершается в PHP-`location`); журнал не содержит `$http_referer`;
  - в том же nginx: в PHP-FPM передаётся только `location ~ ^/index\.php(/|$)`, dot-файлы запрещены `location ~ /\.(?!well-known) { deny all; }`, `GET /storage/x.php` не исполняется (W-20);
  - общий прокси: в примере Caddy по D-35 журнала доступа нет; у nginx-прокси — то же правило `$loggable`;
  - `Referrer-Policy: same-origin`: Referer с токеном уходит только запросам ресурсов своего сайта, чужим — нет; страница — `noindex`, `Cache-Control: private, no-store`;
  - исключение: `error_log` nginx при ошибках (413, таймаут upstream) пишет `request:` и `referrer:` — допустимо, он хранится на сервере с тем же доступом, что журналы приложения.

## 6.3. Вход и сессии

- Штатный Laravel: хеш паролей; `Password::defaults()` с минимумом 8 символов (тот же `minlength` в формах, `autocomplete=current-password/new-password`); `session()->regenerate()` после входа, `invalidate()` при выходе.
- Сессии в БД, зашифрованные: `SESSION_ENCRYPT=true` (иначе `sessions.payload` открыто хранит `_previous.url` — адреса с гостевым токеном, токеном сброса и `client_secret`; W-07, W-20).
- Сброс пароля по письму завершает другие сессии: middleware `AuthenticateSession` (`auth.session`) на маршрутах кабинета и админки, не зависит от драйвера сессий (W-07). Экрана смены пароля нет, как в прототипе.
- Ограничение попыток входа (email + IP и отдельно IP) и запросов сброса; нейтральные ответы.
- Cookie `Secure` (рабочая среда: `SESSION_SECURE_COOKIE=true`, W-20), `HttpOnly`, `SameSite=Lax` (нужно для возврата со страницы Stripe).
- CSRF на всех изменяющих запросах, включая гостевые формы и загрузку. `/webhooks/stripe` и `/webhooks/telegram` проверяют подпись и регистрируются вне группы `web` — без сессии, cookie и CSRF-middleware (список исключений CSRF защитой не считается и не нужен); иначе каждое событие и повтор создавали бы строку `sessions`. Тесты (W-28, W-19): в ответе нет `Set-Cookie`; с включённой проверкой CSRF (в PHPUnit она отключена) webhook без токена получает 400/401/403 по подписи, а не 419.

## 6.4. Файлы

| Правило | Детали |
|---|---|
| Приём | Только STL: по умолчанию 25 МиБ и 500 000 треугольников на файл (как в ядре), до 10 файлов в заявке. Вложения контактной формы — до 5 файлов по 15 МиБ, типы прототипа `.stl,.step,.stp,.obj,.pdf,.jpg,.jpeg,.png`. Медиа администратора (W-08) — по умолчанию 20 МБ (как у Telegram), заданные и в `livewire.temporary_file_upload.rules` (там по умолчанию 12 МБ). Значения — `config/aiqme.php` (в админке не редактируются, как в прототипе), это не утверждённые производственные пределы |
| Пропуск лимитов (W-20) | Встроенные значения малы (php без `php.ini`: `upload_max_filesize=2M`, `post_max_size=8M`, `memory_limit=128M`; nginx `client_max_body_size 1m`). Поэтому: nginx приложения — `client_max_body_size 260m`, `fastcgi_read_timeout 120s`; PHP `conf.d` образа — `upload_max_filesize=25M`, `post_max_size=260M`, `max_file_uploads=20`, `memory_limit=512M`, `max_execution_time=120` (заявка из 10 предельных файлов; анализ 500 000 треугольников при этом `memory_limit` проверяет W-11); общий прокси — Caddy (D-35) `request_body max_size 260MB` (таймаута ответа по умолчанию нет), nginx-прокси — `client_max_body_size 260m`, `proxy_read_timeout 120s` |
| Проверка | Сначала лимит тела на веб-сервере и в PHP, затем фактический размер и структура. STL заявки — `StlAnalyzer` (binary 84 + 50·N байт или ASCII `solid…endsolid`, конечные координаты, объём > 0). Изображения и PDF — по сигнатуре. Медиа контента (W-08, W-19) — только JPEG, PNG, WebP, MP4; SVG не принимается (исполнил бы скрипт на домене сайта). Вложения контактной формы — непрозрачные приватные файлы: размер, число, расширение, PDF/JPEG/PNG по сигнатуре; STL/STEP/OBJ не разбираются (`StlAnalyzer` — только для заявки, W-12), выдаются только `attachment` с `nosniff`. Расширение и MIME — лишь подсказки |
| Хранение | `storage/app/private/…`, имя назначает сервер (UUID), исходное имя — метаданные; sha256; без перезаписи. Публичные медиа (W-08) — имя UUID с расширением по сигнатуре (`.jpg`/`.png`/`.webp`/`.mp4`): nginx берёт Content-Type по расширению |
| Согласованность | Временное место → перенос и связь с записью в транзакции; при ошибке файл удаляется; ночная команда находит сирот и сообщает без автоудаления |
| Выдача | Только контроллер с проверкой прав на каждый запрос, включая HEAD и Range; `Content-Disposition: attachment` с экранированным именем, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`. Подписанных публичных ссылок нет |
| Срок хранения | Модели зарегистрированного клиента — до удаления, без автоочистки (В-066). Файлы гостевых заказов — вместе с заказом; поток анонимных заявок ограничен honeypot и частотой по IP (§3.1). Сроки документов и копий — D-13 |
| Удаление | Клиент скрывает модель из Saved models; файл остаётся у заказа (все сохранённые модели — STL заказов, §1.3). Ручного удаления файлов заказа в MVP нет (в админке прототипа тоже) |

Публичные медиа загружает только администратор; клиентские файлы публичными медиа не становятся.

## 6.5. Webhook и внешние каналы

- Stripe: подпись по сырому телу, допуск по времени, `livemode` соответствует среде, дедупликация `event_id`. Подделка → 400 без эффекта.
- Telegram: `secret_token` (§5.4) и привязанный `user.id`/`chat.id`; дедупликация `update_id`; путь URL секретом не считается.
- Sheets и почта получают минимум данных и ссылку в админку; без вложений, токенов и паролей.

## 6.6. Заголовки, ввод, секреты

- Заголовки отдаёт middleware `SecurityHeaders` (W-03; Stripe-домены — W-16); тесты заголовков и браузерная проверка без нарушений CSP в консоли.
- CSP (enforce):
  - `default-src 'self'`; `img-src 'self' data:` и разрешённые источники медиа; `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`;
  - `script-src 'self' 'nonce-…' 'unsafe-eval'`: nonce на каждый ответ для скриптов Vite и Livewire (`@livewireScripts(['nonce' => …])`); `'unsafe-eval'` — **признанный компромисс**: Alpine в Livewire 3.8.10 вычисляет выражения через `new AsyncFunction`, опции `csp_safe` в этой версии нет;
  - `style-src 'self' 'nonce-…'` (inline-`<style>` Livewire и progress bar получают nonce) с парой `style-src-elem 'self' 'nonce-…'` и `style-src-attr 'unsafe-inline'` — **признанный компромисс**: nonce не действует на атрибуты `style="…"`, а их использует прототип (729 вхождений, в том числе `--sx/--sy/--sw/--sh` спрайтов) и Livewire при морфинге DOM. `<style>`/`<script>` без nonce блокируются; `'unsafe-inline'` в `style-src`/`style-src-elem`/`script-src` не добавляется;
  - для Stripe Payment Element (W-16) — домены официального списка Stripe.js (docs.stripe.com/security/guide, раздел Content Security Policy, сверено 19.10.2026): `script-src https://js.stripe.com https://*.js.stripe.com`; `frame-src https://js.stripe.com https://*.js.stripe.com https://hooks.stripe.com` (3D Secure); `connect-src https://api.stripe.com`. Google Maps (Address Element) и Link не добавляются — эти функции не используются. Повторная сверка со страницей Stripe — W-22.
- HSTS — после подключения домена. `APP_DEBUG=false` в рабочей среде.
- Доверенные прокси — явно из `.env`, не `*`: подсеть внешней сети общего прокси, а если `web` опубликован на `127.0.0.1:<порт>` — шлюз сети проекта (nginx передаёт в FPM как `REMOTE_ADDR` адрес подключившегося). Список читается в момент запроса из конфигурации, не через `env()` в `bootstrap/app.php` (замыкание `withMiddleware` выполняется до загрузки `.env` в PHP-FPM; W-20).
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` — на всех ответах (статику и `/storage/…` отдаёт nginx `web` без PHP и добавляет те же два заголовка, W-20); `Cache-Control: private, no-store` — кабинет, гостевая страница, оплата, админка, выдача файлов.
- Весь ввод — данные: Blade-экранирование, Eloquent с параметрами, санитизация разметки контента, без shell-вызовов с пользовательским вводом. Шаблон счёта — код, не редактируемый контент.
- Секреты только в `.env` (на сервере `root:33`, 0640 — §8.3; ключ Google — там же, §5.3); разные значения для local/test/prod. В логи не пишутся пароли, токены, cookie, гостевые ссылки, payload Stripe целиком.
- Реестр секретов (без значений): `APP_KEY`, БД, `STRIPE_SECRET`/`STRIPE_WEBHOOK_SECRET` (test/live), `TELEGRAM_BOT_TOKEN`/`TELEGRAM_WEBHOOK_SECRET`, SMTP, ключ Google (JSON сервисного аккаунта в base64), ID таблицы.
- Инцидент: сменить затронутые ключи у провайдера → обновить `.env` → сбросить сессии → проверить платежи в Stripe → при необходимости восстановить копию (§8).
