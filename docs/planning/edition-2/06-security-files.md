# 6. Безопасность и файлы

[← План](README.md). Главные риски: чужой доступ к заказам и файлам, ложное «оплачено», потеря принятого заказа, утечка секретов. Модель упрощена: один администратор, без ролей, без MFA (В-044, В-072), но обычная авторизация и права проверяются на сервере.

## 6.1. Субъекты и права

| Субъект | Может |
|---|---|
| Посетитель | Публичные страницы, формы, калькулятор, отправка заявки |
| Гость с секретной ссылкой | Только свой заказ: просмотр, оплата открытых запросов, скачивание своих STL и счетов, ответ администратору |
| Клиент | Свои заказы, модели, адреса, счета; ничего чужого |
| Администратор (`is_admin`) | Всё, включая `/ru/`; создаётся только командой `aiqme:make-admin` |
| Stripe, Telegram | Только свои webhook-маршруты с проверкой подлинности |

- Чужой или несуществующий объект — **404**, не 403: существование не раскрывается. Знание номера заказа, ID или имени файла доступа не даёт.
- Права проверяются в сервисе, а не только в маршруте; Livewire-действия админки повторно проверяют `admin`.
- Клиент никогда не передаёт `paid`, `owner`, `is_admin`, `published`, цену или сумму оплаты. FormRequest + `validated()`, `$fillable`.
- Email из формы не делает человека владельцем гостевого заказа. Привязка гостевого заказа к аккаунту не делается (D-10).

## 6.2. Гостевой доступ

- После отправки генерируется токен 32 случайных байта (base64url). В БД хранится только SHA-256; в URL `/lt/uzsakymas/<номер>/<токен>`.
- Неверный токен — 404; ограничение частоты по IP.
- Администратор может перевыпустить ссылку (старая перестаёт работать) и скопировать её для клиента.
- Ссылка не попадает в Sheets, журналы и Referer (`Referrer-Policy: same-origin`), страница — `noindex`, `Cache-Control: private, no-store`.

## 6.3. Вход и сессии

- Штатный Laravel: хеш паролей, `Password::defaults()`, сессии в БД, `session()->regenerate()` после входа, `invalidate()` при выходе, смена пароля завершает другие сессии.
- Ограничение попыток входа (email + IP и отдельно IP) и запросов сброса; нейтральные ответы.
- Cookie `Secure` (в рабочей среде), `HttpOnly`, `SameSite=Lax` — последнее нужно для возврата со страницы Stripe.
- CSRF на всех изменяющих запросах, включая гостевые формы и загрузку; webhook-маршруты из CSRF исключены, но проверяют подпись.

## 6.4. Файлы

| Правило | Детали |
|---|---|
| Приём | Только STL. Лимиты по умолчанию: 25 МиБ и 500 000 треугольников на файл (как в существующем ядре), до 10 файлов в заявке; вложения контактной формы — до 5 файлов по 15 МиБ, типы прототипа `.stl,.step,.stp,.obj,.pdf,.jpg,.jpeg,.png`. Значения — настройки, не утверждённые производственные пределы |
| Проверка | Сначала лимит тела запроса на веб-сервере и в PHP, затем фактический размер и структура: STL — `StlAnalyzer` (binary 84 + 50·N байт или ASCII `solid…endsolid`, конечные координаты, объём > 0); изображения и PDF — по сигнатуре. Расширение и MIME — лишь подсказки |
| Хранение | `storage/app/private/…`, имя назначает сервер (UUID), исходное имя — только метаданные; sha256; файл не перезаписывается |
| Согласованность | Файл пишется во временное место, переносится и связывается с записью в транзакции; при ошибке удаляется; ночная команда находит сирот и сообщает о них без автоудаления |
| Выдача | Только контроллер с проверкой прав на каждый запрос, включая HEAD и Range; `Content-Disposition: attachment` с экранированным именем, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`. Подписанные публичные ссылки не используются |
| Хранение во времени | Модели зарегистрированного клиента — до удаления, без автоочистки (В-066). Файлы гостевых заказов хранятся вместе с заказом. Сроки документов и копий — D-13 |
| Удаление | Клиент удаляет сохранённую модель, если она не привязана к заказу; модели заказов остаются с заказом. Администратор может удалить файл заказа вручную после завершения — с записью в журнал |

Публичные медиа контента загружает только администратор; клиентские файлы никогда не становятся публичными медиа.

## 6.5. Webhook и внешние каналы

- Stripe: подпись по сырому телу, допуск по времени, `livemode` соответствует среде, дедупликация `event_id`. Подделка → 400 без эффекта.
- Telegram: `secret_token` и привязанный `user.id`/`chat.id`; дедупликация `update_id`; путь URL секретом не считается.
- Sheets и почта получают минимум данных и ссылку в админку; без вложений, токенов и паролей.

## 6.6. Заголовки, ввод, секреты

- CSP (enforce): `default-src 'self'`; `script-src 'self' https://js.stripe.com`; `frame-src https://js.stripe.com https://hooks.stripe.com`; разрешённые источники медиа; `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`. HSTS — после подключения домена. `APP_DEBUG=false` в рабочей среде, доверенные прокси заданы явно.
- Весь ввод — данные: Blade-экранирование, Eloquent с параметрами, санитизация разметки контента, без shell-вызовов с пользовательским вводом. Шаблон счёта — код, не редактируемый контент.
- Секреты только в `.env` (права 0600) и файле ключа Google вне репозитория; разные значения для local/test/prod. В логи не пишутся пароли, токены, cookie, гостевые ссылки, payload Stripe целиком.
- Реестр секретов без значений: `APP_KEY`, БД, `STRIPE_SECRET`/`STRIPE_WEBHOOK_SECRET` (test/live), `TELEGRAM_BOT_TOKEN`/`TELEGRAM_WEBHOOK_SECRET`, SMTP, путь к ключу Google, ID таблицы.
- Короткий порядок при инциденте: сменить затронутые ключи у провайдера → обновить `.env` → сбросить сессии → проверить платежи в Stripe → при необходимости восстановить копию (§8).
