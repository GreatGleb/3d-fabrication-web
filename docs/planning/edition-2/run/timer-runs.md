# Прогон по таймеру и без присмотра — план

Статус: **план, в репозитории не реализован.** Записано 23.10 по итогам прогонов 20–23.10.
Пробные скрипты лежат вне репозитория, в `~/.local/share/aiqme/` и `~/.local/share/aiqme-night/`.
Если решим делать, их надо перенести сюда, в `run/`, и проверить заново.

## Цель

Ноутбук засыпает вечером, просыпается в заданное время (например, 04:58) и сам запускает
`night-run.sh --resume`. Крышка закрыта, присмотра нет, сеть может пропадать.
После прогона ноутбук снова засыпает.

## Что выяснилось 20–23.10

- **Закрытая крышка.** В `/etc/systemd/logind.conf` строка `HandleLidSwitch` закомментирована,
  значит действует значение по умолчанию `suspend`. Если ноутбук проснётся по `rtcwake` с
  закрытой крышкой, через секунду он уснёт снова. Так случилось ночью 22→23.10 и на пробе
  в 23:15. Помогает блокировка
  `systemd-inhibit --what=sleep:handle-lid-switch` на всё время прогона. 20–22.10 с ней
  прогоны шли при закрытой крышке. Когда блокировка снимается при закрытой крышке, logind
  сразу усыпляет ноутбук. Это и есть нужное «уснуть после прогона», отдельная команда не нужна.
- **Сеть после пробуждения.** Если ждать фиксированные 20 секунд, этого мало: Claude отвечает
  `EAI_AGAIN`, и `night.py` останавливается с `BudgetUnknown`, потому что нет `modelUsage`.
  Запускать прогон нужно только после удачного `curl https://api.anthropic.com`. Пользователь
  часто подключается через USB-модем при выключенном Wi-Fi, поэтому нужен ещё
  `nmcli radio wifi on`. Сам подключиться ноутбук может только к уже известной сети.
- **Сеть пропадает посреди прогона.** Claude не всегда сразу возвращает ошибку. Надёжнее
  внешний сторож: если проверка `curl` не проходит 4 раза подряд с шагом 30 секунд, он
  останавливает `night.py` и сессию `claude --print` (обе группы процессов), убирает работу в
  `git stash push -u -m "night-blocked W-xx"` и пишет заметку в `progress.md`. Следующий
  `--resume` подхватывает такую работу. Супервизор ждёт сеть и перезапускает прогон до общего
  срока. 21.10 так прошли два обрыва без потерь.
- **sudo.** Ему нужен пароль. Пароль, введённый в начале скрипта, к утру уже недействителен,
  поэтому `sudo` после пробуждения повиснет. Пароль нужен только для `rtcwake`, и вызывать его
  надо последним действием перед сном. Настройки logind и GNOME не трогать.
- **Лимит.** После каждого перезапуска `night.py` считает потолок токенов заново. При
  перезапусках супервизором общий расход может превысить 15 % недели. Если делать это всерьёз,
  нужен общий счётчик токенов на весь срок.

## Схема

1. `night-at.sh ЧЧ:ММ [часов]`, запускается из терминала вечером:
   - проверяет, что в дереве нет незакоммиченных изменений (иначе `night-run.sh` не стартует);
   - один раз запрашивает пароль `sudo -v`;
   - запускает службу
     `systemd-run --user --unit=aiqme-morning systemd-inhibit --what=sleep:handle-lid-switch morning-run.sh`;
   - выполняет `sudo rtcwake -m mem -t <время>`.
2. `morning-run.sh` (внутри службы):
   - ждёт, пока наступит время пробуждения;
   - до 30 минут ждёт интернет, включая Wi-Fi;
   - запускает прогон со сторожем сети, затем супервизор до срока.
3. Когда прогон закончится, служба завершается и блокировка снимается. Если крышка закрыта,
   ноутбук засыпает.

Не проверено целиком: пробуждение по `rtcwake` при уже взятой блокировке. Сначала прогнать
коротко, с будильником через 3 минуты и закрытой крышкой.

## Альтернативы

- Системный таймер с `WakeSystem=true` вместо `rtcwake`. Нужна системная служба, то есть права
  root при установке, зато пароль ночью не нужен.
- Не усыплять ноутбук вовсе: на ночь включён только запрет сна, прогон запускается по
  `systemd-run --user --on-calendar=…`. Это проще, но ноутбук всю ночь не спит.
