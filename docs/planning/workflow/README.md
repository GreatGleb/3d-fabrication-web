# Последовательный workflow плана AIQME

> 18 октября 2026 план переработан вручную в [редакцию 2](../edition-2/README.md). Каталог `docs/planning/run/` помечен `superseded_by`: `run` и `preview` для него остановятся с сообщением, `status` работает. Новый запуск этого 30-слойного workflow не нужен. Задачи реализации — [tasks.json](../edition-2/tasks.json); это другой формат, оркестратор для них пока не создан.

Запуск из корня проекта, Python 3.10+ и авторизованный Codex CLI.
Скрипт ищет `codex` в PATH, затем в локальных установках, включая расширение
`openai.chatgpt` в VS Code. Найденный путь печатается перед запуском.
При необходимости укажите его явно: `--codex /полный/путь/к/codex`.
Скрипт использует установленную модель и настройки Codex; модель можно явно задать
через `--model`. Каждый автор и проверяющий запускается в новой сессии `codex exec`.
Основание интерфейса CLI: [официальная документация](https://developers.openai.com/codex/noninteractive/).

```bash
# Посмотреть задание первой/следующей сессии без вызова модели
python3 docs/planning/workflow/plan_workflow.py preview

# Весь цикл; повтор той же команды продолжает с первого непринятого слоя
python3 docs/planning/workflow/plan_workflow.py run

# Пробный запуск одного слоя с независимой проверкой
python3 docs/planning/workflow/plan_workflow.py run --until 1

# Прогресс, вопросы и фактически зарегистрированные токены
python3 docs/planning/workflow/plan_workflow.py status
```

По умолчанию результат: `docs/planning/run/PLAN.md`, подробности в `sections/`.
`state.json` — единственный источник состояния: принятые разделы, краткое содержание,
открытые вопросы и история результатов. Восстановление производных Markdown-файлов
автоматическое. Не редактируйте их вручную: изменения будут перезаписаны.
Исходные требования в `docs/requirements.md` автоматически не изменяются;
расхождения с ними фиксируются в плане для последующего согласования.

Задания 30 слоёв и рекомендуемые зависимости находятся в `layers.json`.
Каждый слой обязан иметь основания и выполненные проверки. Скрипт проверяет
структуру JSON, идентификаторы разделов/вопросов, обязательное содержимое и размер
кратких сводок. Проверяющая модель проверяет смысл, соответствие источникам и
сохранность прежних деталей. При отказе автор получает замечания и путь к кандидату.
До трёх попыток на слой за один запуск (`--attempts`). После исчерпания попыток
workflow останавливается, замечания сохраняются; повторный запуск получает их.
Ошибка CLI, тайм-аут или блокер также останавливают процесс без принятия слоя.
Невалидный JSON/несоответствие основной схеме останавливает запуск; семантические
ошибки структуры (например, неверные номера разделов) направляются на исправление.

По умолчанию это **30 авторских сессий + 30 проверяющих**, без учёта исправлений.
Для более экономного режима проверка раз в пять слоёв (30 + 6 сессий):

```bash
python3 docs/planning/workflow/plan_workflow.py run --output docs/planning/economy --review-every 5
```

В этом режиме промежуточные слои принимаются после программной проверки, а проверяющий
на контрольной точке проверяет весь блок. Слой 30 всегда проверяется. Частоту нельзя
менять внутри существующего запуска. Независимая проверка моделью не гарантирует
отсутствия ошибок; подтверждения заказчика и экспериментальные измерения сохраняются
как отдельные условия начала реализации.

## Контекст и расход

Вместо растущей истории диалога сессия получает индекс принятых разделов (до 700
символов на раздел), последнюю передачу (до 2500), все открытые вопросы и сложности
прошлых слоёв. Детальные разделы читаются по путям зависимостей; прочее — по необходимости.
Сырые логи предыдущих сессий не включаются. Общие инструкции AGENTS и входные документы
по-прежнему обязательны. На итоговом аудите полный план читается намеренно.
Списки вопросов и сложностей не обрезаются: это защищает от потери проблем, но не
даёт строгой верхней границы контекста. Модель сама решает, сколько файлов прочитать.

`sessions/` содержит задания, кандидатов, замечания, JSONL-события, stderr и метрики.
`status` суммирует input/output/cached input из событий `turn.completed`, включая
непринятые попытки. Cached input не прибавляется повторно к общему input.
Это учёт токенов, не стоимости. Прерванные процессы могут не сообщить usage.

```bash
python3 docs/planning/workflow/plan_workflow.py run --max-total-tokens 500000 --timeout 1800
```

Порог проверяется **между сессиями**, учитывает историю запуска и может быть превышен
одной сессией. Это не жёсткий лимит тарификации. `--timeout` ограничивает время одной
сессии в секундах. Ctrl+C завершает группу запущенного процесса; повтор команды
продолжает с непринятого слоя. Кандидат, уже полученный до прерывания проверки, остаётся
в логах; при возобновлении автор запускается заново. Закрытие терминала/перезагрузка
не обеспечивают автоматический рестарт: используйте обычный терминальный менеджер
сеансов при длительном запуске. На один каталог допускается только один процесс.

## Новые материалы и границы работы

Основные источники уже заданы в скрипте. Дополнительные правки передайте при первом запуске:

В источники включены `docs/customer-prototype/prototype-browser.md`, скрипт CDP и сохранённый снимок
`docs/customer-prototype/evidence/20261015-214335/`: манифест, DOM, PNG и перечисленные
ресурсы. Их содержимое не вставляется целиком в каждый запрос: сессии получают пути.
Слои 1, 2, 8–10, 26 и 30 получают дополнительные указания по изучению снимка.
Хеши файлов снимка также контролируются; новый каталог не подхватывается автоматически.

Основной способ нового просмотра — CDP из [инструкции](../../customer-prototype/prototype-browser.md).
AT-SPI больше не предлагается как основной путь. Озвучивание не включать.
Пользователь разрешил сессиям самостоятельно изучать сайт по необходимости, включая
другие страницы, языковые версии, тексты, DOM, вычисленные стили и загруженный CSS/JS.
Для такого чтения не требуется отдельное разрешение или предварительная выгрузка
снимка. Сессия может открыть свою вкладку, исследовать навигацию, меню, прокрутку и
адаптивность, затем закрыть только свою вкладку. Отправка форм и изменение данных
не входят в исследование. Серверные исходники через браузер могут быть недоступны.
Результаты, URL и дата сохраняются в разделе плана и evidence; следующие сессии
используют их и подключаются повторно только для нужных им проверок.
Авторы работают в read-only и не запускают сборщик снимка, который пишет файлы.
Чтение через CDP выполняется без записи файлов, используя способ подключения из сборщика.
Если для плана нужен свежий снимок, выполните его сбор отдельно по инструкции,
добавьте его манифест через `--source` при новом запуске и сохраняйте старый снимок.
Дополнительный манифест фиксируется как источник, но его ресурсы автоматически
не хешируются; при необходимости добавляйте их отдельными `--source`.

Пример добавления новых правок:

```bash
python3 docs/planning/workflow/plan_workflow.py run --source '/полный/путь/к/новым правкам.txt'
```

Список сохранится для продолжения. Контрольные суммы входных материалов и `layers.json`
проверяются перед продолжением и принятием слоя. Если они изменились, нужен новый
`--output`: старые решения требуют переоценки. Это не полный снимок репозитория —
не меняйте исходный код во время планирования. Внешние страницы также могут измениться;
сессии должны фиксировать дату и основания своих выводов.

Сессии запрашивают sandbox `read-only`, а Python записывает только результаты в каталог
запуска. Исходники сайта, публикация, baseline и instance не изменяются оркестратором.
Запрет внешних операций записи также включён в задания. Read-only sandbox ограничивает
локальные команды, но не является фильтром прав подключённых MCP-сервисов; для строгой
изоляции запускайте CLI с конфигурацией, содержащей только необходимые инструменты чтения.
Доступ к Chrome/подключениям текущего чата не гарантирован в дочернем CLI. Если прототип
недоступен, это должно остаться открытым вопросом, а не выдуманным результатом просмотра.

Логи могут содержать клиентские материалы: не публикуйте каталог запуска.
Workflow только готовит план; не запускает разработку, оплату, отправку сообщений или деплой.

## Проверки самого workflow

```bash
python3 -m unittest discover -s docs/planning/workflow -p 'test_plan_workflow.py' -v
```

Тестовая подмена CLI проверяет 30 слоёв, возобновление, замечания после отказа,
изменение источников, порог токенов и валидацию результатов. Она не доказывает
доступность модели/авторизации/Chrome: это проверяется пробным реальным слоем.

## Расположение и генератор задач

С 18.10.2026 скрипт, `layers.json`, тест и этот README лежат вместе в `docs/planning/workflow/`
(раньше `scripts/`, `tools/planning/`, `tests/`). Исторический `docs/planning/run/state.json`
хранит прежние абсолютные пути входов в `source_hashes`; он не переписывался, поэтому `run`
для этого цикла остаётся заблокированным `superseded_by`, а `status` работает.

`render_tasks.py` строит [tasks.md](../edition-2/tasks.md) из [tasks.json](../edition-2/tasks.json):

```bash
python3 docs/planning/workflow/render_tasks.py          # перегенерировать
python3 docs/planning/workflow/render_tasks.py --check  # проверить актуальность
```
