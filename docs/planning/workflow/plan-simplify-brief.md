## Почему

План прошёл проверку 19.10 (blocker и major нет), но за 11 раундов разросся: 32 задачи, D-01…D-42,
около 87 тыс. слов в edition-2. Отдельные решения (D-21, D-28, D-39) занимают страницу сплошного текста.
Длина сама стала риском: ночной агент читает план в каждой сессии заново, и чем длиннее правило, тем
вероятнее, что он его пропустит или поймёт неверно.

## Что считается упрощением

1. **Одно место для каждого правила.** Если правило описано в нескольких файлах — полный текст остаётся
   в одном (обычно раздел 0x или decisions.md), в остальных — одна строка со ссылкой.
2. **Исполняемое вместо описанного.** Длинные инструкции, которые агент или пользователь выполняет
   буквально, переносятся в готовые файлы в `docs/planning/edition-2/run/`, а в плане остаётся
   короткое правило и ссылка:
   - `run/claude-settings.local.json` — allow/deny-правила D-28 для Claude Code;
   - `run/codex-command.md` — команда запуска Codex по D-28 (короткая);
   - `run/preflight.sh` — предпроверка W-01 (D-28, D-30, D-39): каждая проверка печатает OK/FAIL,
     код возврата ≠ 0 при любом FAIL;
   - `run/prepare-aiqme-run.sh` — подготовка учётной записи по D-39 шаги 0–2 (выполняет пользователь
     с sudo; скрипт идемпотентный, параметр — путь к корню пользователя; ничего не делает без
     подтверждения на каждом шаге с sudo);
   - `run/return-results.sh` — возврат результата по D-39.
   Эти файлы НЕ запускать. Секретов в них нет и быть не должно (репозиторий публичный).
3. **Решение — коротко.** Каждое D-xx в decisions.md: что решено (1–3 предложения), почему (1 предложение),
   ссылка на исполняемый файл или раздел, где подробности. История обсуждения и альтернативы,
   которые пользователь отклонил, — одной строкой или в changes.md.
4. **Задача — коротко.** В tasks.json у задачи: цель, входы, что сделать, критерии «готово», проверки.
   Объяснения «почему» и ссылки на раунды проверки из задач убрать (они есть в changes.md и review).
   Критерии «готово» не ослаблять и не удалять — только сокращать формулировку.
5. **История — отдельно.** changes.md и review-*.md — исторические; ночной агент их не читает
   (если это ещё не сказано в `rules` tasks.json — одна строка в `rules`). Их не сокращать.

- Добавлять новые правила и функции «для полноты». Если при упрощении найдено противоречие — не
  исправлять самому, записать в отчёт как замечание.

**Шаг 0. Снимок.** Скопируй docs/planning/edition-2/ в `simplify/before/` и посчитай слова по файлам
(`wc -w`) — это база для сравнения.

**Шаг 1. Упрощение — параллельно, у каждой подсессии свои файлы (чтобы не было конфликтов правок):**
- A: decisions.md и файлы `run/` (сначала создать файлы `run/`, затем сократить D-xx со ссылками на них);
- B: tasks.json (затем render_tasks.py);

Каждая подсессия может читать всё, а править — только свои файлы. Ссылки на чужие файлы — по
текущим якорям; если подсессия хочет, чтобы правило ушло из чужого файла, пишет это в отчёт, а не правит.
Отчёт: что сокращено, что перенесено куда, просьбы к другим файлам.

**Шаг 2. Сведение.** Выполни просьбы между файлами одной подсессией-исправителем (одна, последовательно).
Затем: render_tasks.py и --check; tasks.json — валидный JSON в прежнем формате;
`python3 docs/reorganization/20261018/tools/check_links.py .` → broken=0.

**Шаг 3. Проверка потерь — параллельно, по одному проверяющему на группу A–E.**
Проверяющий сравнивает `simplify/before/` с текущими файлами (diff) и по каждому удалённому или
сокращённому фрагменту отвечает: смысл сохранён (где именно) / потерян (что) / изменён (как).
Отдельно: файлы `run/` соответствуют правилам D-28/D-30/D-39 из `before/` (каждое allow/deny-правило,
каждая проверка предпроверки, каждый шаг подготовки и возврата). Новых замечаний к плану не ищет.

**Шаг 4. Возврат потерь.** Всё «потеряно» и «изменено» — исправителю (вернуть смысл коротко), затем снова
шаг 3 только по этим пунктам. Не больше двух повторов; что не закрылось — в отчёт.

**Шаг 5. Чтение глазами ночного агента.** Две свежие подсессии параллельно. Каждая берёт только

искать правило в нескольких местах. Замечания — в отчёт (исправлять только явную потерю смысла).
