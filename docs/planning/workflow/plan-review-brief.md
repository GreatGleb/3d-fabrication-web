## Раунд (повторяется)

### Шаг 1. Скептики — параллельно, по одному на каждую ОТКРЫТУЮ тему

Каждый скептик новый (свежий контекст), только читает, пишет отчёт `review/r<N>-T<k>-skeptic.md`.
Угол зрения меняется по раундам, чтобы повторный взгляд был другим, а не таким же:

- нечётный раунд — **спецификация**: противоречия между файлами, requirements.md, аудитом и D-xx;
  требования без задачи и задачи без источника; факты о версиях, путях, файлах (по диску, composer.lock
  экспериментов; внешние — по официальным источникам);
- чётный раунд — **прогон глазами ночного агента**: пройти задачи своей темы в порядке tasks.json и на
  каждой ответить: что уже есть на диске к этому моменту; что агенту придётся угадать; докажет ли
  проверка, что функция работает (или пройдёт при неработающей); влезает ли задача в одну сессию.

Скептик T5 в каждом раунде смотрит стыки между темами: задача опирается на то, что создаётся позже;
один и тот же объект описан в двух файлах по-разному; проверка зависит от приватного файла или сети.

Всем скептикам: риски безопасности (оплата, права, файлы, секреты; корень — ПУБЛИЧНЫЙ репозиторий) и всё,
где ночному агенту придётся гадать. Принцип плана: максимально просто, только то, что просил заказчик и
показывает прототип; объём ради «полноты» не раздувать.

Скептик получает реестр: замечания со статусом «проверено» или «отклонено» не повторяет, если нет
НОВОГО доказательства (тогда — явно «переоткрыть ID» с доказательством).

Формат замечания: ID `R<N>-T<k>-NN`, серьёзность, файл и место, доказательство (цитата/путь),
почему проблема, направление исправления. Плюс отдельный список «нужно решение пользователя» — только
то, что нельзя решить без данных, денег или вкуса заказчика, с вариантом по умолчанию.

Серьёзность (строго):
- **blocker** — ночной агент не сможет выполнить задачу или сделает опасное (оплата, права, секреты);
- **major** — агент с высокой вероятностью сделает НЕВЕРНО, или проверка задачи будет ложно-зелёной,
  или задача зависит от того, чего ещё нет;
- **minor** — всё остальное, включая узкие технические уточнения, которые агент решит сам по документации
  (их исправитель может вписать пометкой в задачу, но они не держат тему открытой).

### Шаг 2. Сведение

Ты объединяешь отчёты в реестр: убираешь дубли (одна проблема из двух тем — одно замечание), ничего не
отбрасываешь по существу.

### Шаг 3. Исправитель — один

Один исправитель на раунд (файлы плана общие — параллельные правки tasks.json конфликтуют). Получает
только список открытых замечаний из реестра. По каждому: исправляет план (tasks.json, разделы edition-2,
decisions, traceability, changes, requirements при необходимости) либо обоснованно отклоняет со ссылкой
на источник. Решения за пользователя не придумывает: выносит в decisions.md как D-xx с вариантом по
умолчанию и пометкой «требуется решение пользователя». Исправляет причину, а не формулировку: найди ВСЕ
места плана, где описан тот же объект, и приведи их к одному виду. После правок: render_tasks.py и
--check; tasks.json — валидный JSON в прежнем формате; ссылки целы
(python3 docs/reorganization/20261018/tools/check_links.py . → broken=0).
Возвращает таблицу «ID → исправлено (какие файлы) / отклонено (почему) / вынесено в D-xx».

### Шаг 4. Проверка исправлений — параллельно, по одному проверяющему на тему

Новые подсессии. Каждая получает замечания своей темы из этого раунда, ответ исправителя и `git diff`
файлов плана. Отвечает по каждому ID: закрыто полностью / закрыто частично (что осталось) / исправление
сломало другое место (где). Новых замечаний вне diff не ищет — это работа скептиков.
Незакрытое — обратно исправителю (шаг 3 → шаг 4), не более 2 повторов за раунд; дальше — в реестр как
открытое на следующий раунд.

### Закрытие темы

Тема закрыта, когда свежие скептики ДВУХ раундов подряд (то есть оба угла зрения) не нашли в ней
blocker и major, а все её замечания «проверено» или «отклонено». Закрытые темы в следующих раундах не
проверяются, кроме T5 — она идёт до конца, пока открыта хоть одна тема.
