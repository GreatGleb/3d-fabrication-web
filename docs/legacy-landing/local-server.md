# Локальная серверная версия

> Прежний лендинг после реорганизации 18.10.2026 находится в `legacy-landing/`. Все команды и пути ниже выполняются и читаются **из каталога `legacy-landing/`** (`cd legacy-landing`); скрипты не зависят от текущего каталога, поэтому из корня можно вызывать их с префиксом, например `python3 legacy-landing/scripts/build_pages.py`.

`server/app.py` обслуживает `build/server/`; база и вложения по умолчанию остаются в `instance/`. Переменная `AIQME_DATA_DIR` позволяет выбрать другую директорию данных. Существующие данные при реорганизации не изменялись, их назначение и актуальность не подтверждены.

```bash
python3 -m pip install -r requirements-server.txt
python3 scripts/build_pages.py
python3 server/app.py serve
```

Адрес: http://127.0.0.1:8820/ . Для новой отдельной базы предусмотрена команда `python3 server/app.py init`; текущие данные без необходимости не переинициализируйте.

Клиенты и проекты создаются через консоль, без открытой регистрации и админки:

```bash
python3 server/app.py create-client client@example.com
python3 server/app.py add-project client@example.com "Корпус датчика" --summary "Подготовка модели"
python3 server/app.py set-status 1 "В работе"
python3 server/app.py attach-file 1 /path/to/model.stl
python3 server/app.py set-password client@example.com
python3 server/app.py list-leads
python3 server/app.py show-lead 1
```

Пароль вводится интерактивно. Формы сохраняют заявки и вложения локально; уведомлений на почту и записи в Sheets пока нет. Клиенты видят свои проекты и файлы. Проверка изоляции: `python3 scripts/check_portal.py`, использует временную базу.

Для старой серверной модели при реальном размещении понадобились бы HTTPS, `AIQME_HTTPS=1`, постоянное хранилище и WSGI-сервер. Но архитектура будущей платформы ещё не утверждена; это инструкция существующей реализации, не выбор будущего хостинга.

### Что использовать и доработать

- Сохранить `create_app`, управление соединением/закрытием БД на запрос, параметризованные SQL-запросы, хеширование паролей, CSRF и проверки владельца файла. Для нового кабинета расширить модель и маршруты. Вместо дальнейшего роста одного файла разделить обработчики по входу, заказам, контенту и интеграциям.
- Самостоятельной регистрации и восстановления пароля, прав единственного администратора, заказов/платежей/счетов, редакторов контента и интеграций пока нет. Таблицы `users`, `projects`, `project_files`, `leads` не заменяют модель заказов и оплат. Новые схемы и их изменения нужно оформлять явно; `CREATE TABLE IF NOT EXISTS` не обновляет структуру существующих таблиц.
- Оплата и ход производства должны учитываться раздельно; суммы подтверждает сервер, запрос оплаты и её подтверждение провайдером — разные операции. Текущий калькулятор даёт предварительную браузерную оценку.
- Для Telegram, Sheets и почты нужны сохранённые задания, повторы и проверяемый результат; одного фонового потока внутри HTTP-запроса недостаточно для сохранения работы после перезапуска. Конкретный механизм не выбран, обязательства использовать Celery/Redis нет.
- Изменить обработку нескольких вложений/моделей. Текущий лимит HTTP-запроса 26 MiB не равен поддержке нескольких STL до 25 MiB каждый. Проверка расширения файла в старой заявке не заменяет анализ содержимого STL и ограничения общего объёма.
- Исправить отзыв сессий и определить сроки их действия. Адаптировать ограничение попыток и реальные IP к выбранному reverse proxy: текущий `request.remote_addr` без настройки доверенных прокси может объединить всех посетителей в один лимит заявок. Доверять произвольному входящему X-Forwarded-For нельзя.
- Проверить CSP при интеграции: текущий заголовок допускает только собственные script/style/connect и не разрешает inline-код, внешние платёжные ресурсы или blob-видео автоматически. Согласовать политику с реальными ресурсами прототипа и выбранной оплатой.
- SEO совместимо с Flask: публичные LT/EN страницы можно отдавать готовым HTML из шаблонов/сборки. При переносе нужны реальные маршруты, локализованные title/meta, canonical/hreflang, sitemap и верные HTTP-статусы. Сам выбор Flask не делает сайт SEO-оптимизированным.

SQLite в текущем приложении проверена функционально. Для предполагаемого небольшого потока её можно рассматривать как начальный вариант на одном сервере с постоянным диском, но параллельные записи, восстановление резервной копии и пределы нагрузки здесь не проверялись; выбор БД остаётся отдельным решением. Существующие данные переносить не требуется.

Для публикации использовать production WSGI-сервер, HTTPS, постоянные данные и резервирование. `python3 server/app.py serve` запускает сервер разработки и не является способом рабочего размещения. Официальные источники: [развёртывание Flask](https://flask.palletsprojects.com/en/stable/deploying/), [запуск factory через Gunicorn](https://flask.palletsprojects.com/en/stable/deploying/gunicorn/), [доверенные прокси](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/), [соединения SQLite](https://flask.palletsprojects.com/en/stable/patterns/sqlite3/).
